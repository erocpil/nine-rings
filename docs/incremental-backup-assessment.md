# 按文档增量 GitHub 备份建议评估

> 2026-10-10；评估 `~/Downloads/sync-incremental-design.md` 及更新版 `sync-incremental-design (1).md`，核对当前源码及 github.com 官方 REST 文档。属于设计评估，不表示增量备份已经实现。当前仍是版本化全量 JSON 备份；本批没有写入远端备份仓库。文末补 v2 采纳意见和第 13 节八项回复。

## 结论与现状修正

采纳“按稳定文档身份拆文件、确定性编码、复用 Git tree 的增量传输、保留共同基线、非强制发布”这一方向。根据 v2 的实测规模，先做现有快照的语义与测量补强，按实际传输、仓库增长与跨端需求决定是否迁移；不因正文约 10 MiB 就立即换格式。保持用户触发、预检和安全合并；删除传播、字段自动合并和历史清理分开交付，避免把格式升级扩大为一次难以回退的行为变更。用户已确认所有可构建版本都可能 Push/Pull，可能同时编辑同一文档，暂不需要自动同步。

草案未读源码，因此两处现状需要修正：

- Web/PWA/Tauri **已有三方比较**。`src/lib/sync/github.ts` 的 `fetchBaseSnapshot` 获取最近已知 Push/Pull 的共同快照，`src/lib/sync/backup-merge.ts` 根据规范化内容身份分类本地改动、远端改动和真正冲突；无基线时保守处理。它不依赖 updated_at 决定哪份更新。增量方案应复用其规则及冲突决定过期校验，不重做一套两方恢复。
- Push 使用 Contents REST API 创建 `{path}-{version}.json` 全量快照，再按旧 SHA 更新 `{path}-latest` 指针；并非反复覆盖一个同名 JSON，也不是原生 Git 或 Git Trees 上传。最新指针发布失败可留下未发布快照，已有旧设备 Push 保护。全量传输、快照文件累积及跨端编码差异仍是实际问题。

Flutter 已有旧设备 Push 保护，但 Pull 不具备 Web 的安全三方合并；加密工作区会被明确拒绝。不能把“已有三方比较”推广为所有客户端已等价。

## 逐项采纳意见

| 建议 | 判断 | 落地调整 |
| --- | --- | --- |
| 每文档一个 JSON，以 ID 命名 | 采纳 | 使用专用命名空间/分支、稳定安全编码；既有导入接受非空字符串 ID，不能假定历史 ID 全是 UUID，也不能重新分配身份 |
| 目录分片 | 暂不预设 16 片 | 当前规模可平铺，但使用安全 ID 编码并声明 layout；不因接近 800 篇就自动迁移。Trees API 检查 truncated 并提供完整遍历回退，目录浏览限制不等于备份容量限制 |
| Git tree 的 base_tree 与条目 content | 采纳 | 增量树必须基于完整当前树，保留命名空间外文件；content 是官方支持，不需重新证明功能存在，实际载荷与批大小仍要测量 |
| 确定性编码及跨端向量 | 必须 | 固定字段别名、null/省略、时间戳、浮点/整数、嵌套键、UTF-8 字节长度与换行；Tauri 可复用共享 TS 编码器，Flutter 用向量对拍，不必重复实现第三套 Rust 编码器 |
| 所有 Unicode 统一 NFC | 不按原文采纳 | 正文/代码/原始 Markdown 的 Unicode 必须原样保留；路径 NFC 碰撞应按 A4 单独报告与迁移，不能在同步中静默改写 |
| tags/concepts 排序 | 有条件 | 先定义数组是否为集合；仅对明确无序字段生成规范投影，不改写 UI 原顺序；正文 Delta、列表、关联等有序数组不得通用排序 |
| baseBlobSha 三方比较 | 复用并扩展 | SHA 可比较整文档，但字段合并需要可获取基线正文/字段值；缓存基线或保留可读取的基线对象，不能只有 SHA |
| 元数据字段级合并 | 后续独立批次 | 先处理确实独立的字段。storagePath 与路径保护、密钥标识、密文属于关联组；正文与源码、书签、引用锚点不能拆开拼接成失配模型 |
| 软删除/硬删除自动传播 | 暂缓默认开启 | 当前安全合并不传播删除；要有完整快照证明、墓碑/删除代次、保留期限及旧客户端策略。首次还原、忽略项、截断树、失败下载或权限不足不表示删除 |
| 空闲/后台自动同步 | 后续独立设置 | 首版保留手动 Push/Pull；后台只尽力执行，手机挂起/页面关闭没有完成保证；复用保存屏障与恢复互斥锁，加入有界重试与可恢复任务 |
| 初始迁移分批 | 采纳原理 | 按 UTF-8 请求字节预算分批，而非固定 100 篇；在暂存区域准备并验证后一次发布完整格式，不让半迁移树被识别为完整备份 |
| 原生 Git/tarball | 作为后续优化 | 桌面仍复用 REST；当前未集成 Git 进程/凭证管理。私有归档的重定向、Web CORS、令牌隔离、解压预算和实际速度需实验 |
| 定期压历史并打标签 | 不作为默认操作 | 新快照提交不会删除历史；保留旧标签仍使旧对象可达。物理回收需要处理引用和服务端回收，不承诺标签保留全部历史又释放其空间 |
| L0 包一起同步 | 分离审批 | 安装包、启用状态、授权及私有数据不是一件事；备份还原不能自动安装、信任或执行插件，依赖 R7 的完整性/信任门禁 |

## 保存与同步一致性

本次已实现的 `DocumentSaveRevisions` / `AutoSaveQueue` 只提供本机自动保存修订与字段确认基础，不是跨设备版本或 Git 提交身份。增量任务应冻结已保存的本地快照与对应逻辑修订，再做编码和网络传输；上传期间的新编辑留给下次备份，不能随着远端请求成功把全部本地状态标为已同步。

同步基线必须按仓库所有者、仓库、分支、根命名空间、格式和编码版本隔离。需要每实体的已合并基线以及忽略/冲突处理状态，不能读取新的远端 HEAD 后就认为所有远端文档已接受。下载内容按固定 commit/tree/blob 获取，不跟随移动的 HEAD 混读。

发布使用父提交与 `force: false`。并发设备从同一父提交生成分叉时，后发非快进更新会被拒绝，重新获取远端并比较后才可重试；这不是任意场景下的严格 expected-HEAD 比较交换。超时/取消可能发生在服务端已发布之后，重试前查询实际提交，不能盲重放写入。分支规则、403/429/409/422、限流和连续竞争都应有界处理。

Pull 应先校验完整资源清单与所有内容，再检查预检以来的本地修订，经过恢复协调器提交；导入与基线确认之间崩溃要有可恢复日志。远端发布与本地确认不是一个原子事务，本地确认失败不能误称远端未发布。

## 加密、图片与版本

当前文档加密已经存在：AES-GCM 密文含随机 IV；Push 导出已存密文，不会每次上传重新加密。因此可对**既有密文字节**产生稳定传输哈希，无需解锁，也不上传明文哈希。以后若需要识别“重加密但明文相同”，只能另行设计受保护的本地指纹或带密钥协议，不能把公开明文 SHA 作为默认远端元数据。Git blob ID 是对象身份，不是签名或独立可信校验；格式可另外包含 SHA-256 完整性摘要。

普通文档历史在独立 `note_versions` 中，本次 JSON 不包含；加密文档历史以 `protected_versions` 包含。不能以“本机已有历史”为由删除远端历史，因为新设备并没有普通文档的这些本机版本。未来是否同步普通版本，应明确范围、保留政策及独立资源布局。

现有 Web/Tauri 导出将本地图片引用内嵌为 data URI；加密内容中的图片也需要保持加密边界。初版可保持现有表达，后续根据测量将大附件拆为稳定资源对象，并处理共享引用、缺失资源、保护范围和安全回收。PDF/EPUB 独立资料库需要单独资源协议与恢复协调，不能只增加 config 文件就声称覆盖它们。

## 官方约束复核与需测量项

- GitHub 文件限制为 50 MiB 警告、100 MiB 阻止；现有 API 整体载荷也要单独考虑，不能把文件极限作为安全批大小。[大文件说明](https://docs.github.com/en/repositories/working-with-files/managing-large-files/about-large-files-on-github)
- Contents 的目录列表上限为 1000 条；文件读取按 1 MB/100 MB 分级。已知路径逐文件读取不依赖目录列表，因此 1000 篇不意味着必须改变分片算法。[Contents API](https://docs.github.com/en/rest/repos/contents)
- Trees 官方支持 base_tree、条目 content 和删除 sha:null；递归列表有 100000 条/7 MB 限制。遇到截断不能推断未出现文档已删除。[Trees API](https://docs.github.com/en/rest/git/trees)
- 认证 PAT 通常 5000 请求/小时；次级限制一般包括每端点 900 点/分钟、创建内容 80 次/分钟与 500 次/小时，GET 常为 1 点、写请求常为 5 点，存在未公开或更低限制。这不是性能承诺，不能据此保证 1000 个 blob 一两分钟下载完成。[REST 限流](https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api)
- 更新引用 `force:false` 保证快进，需结合新提交父节点及重新比较处理竞争；Git Blobs 读取支持至 100 MB。[Refs API](https://docs.github.com/en/rest/git/refs)、[Blobs API](https://docs.github.com/en/rest/git/blobs)

未执行受认证的树写入、私有 tarball/CORS、1000 篇下载测速或任何远端迁移。本机 content 字节统计也不能证明“几十 MB 序列化亚秒”；须测 Worker/主线程时间、峰值内存和手机耗时，批量读取及编码不能重新引入长文档浏览卡顿。

## 推荐分批顺序与验收

1. **I0 范围与测量**：只输出聚合的导出统计，固定本机快照边界与实体范围，补普通/保护/图片/随记/设置的恢复矩阵。
2. **I1 规范与向量**：新 Git 布局单独声明 kind/format，区别现有 JSON version 1/2；确定编码与 ID 路径策略、未知字段和字段关联组。共享 TS 服务兼容 Web/Tauri，Flutter 暂不安装本地工具，但 CI/格式契约不可遗漏。
3. **I2 传输试点**：沿用手动操作、安全合并与不传播删除；同一 commit 的完整读取、树截断回退、字节预算、取消/限流、并发发布与结果不明恢复。改 5 篇只传 5 篇，无改动不创建提交。
4. **I3 基线持久化与恢复**：按实体/仓库隔离、原子更新或恢复日志、忽略项不误确认、导入期间编辑冲突。正文先保持整体冲突处理，再试独立元数据字段合并。
5. **I4 迁移与客户端边界**：保留原全量快照及还原能力，校验完整新树后发布；旧客户端不理解新格式，不能承诺自动看到新格式产生的后续更新。要明确分支隔离、拒写/升级提示或显式兼容快照，不能靠改 format 数字解决。
6. **I5 可选同步语义**：显式开启的删除/墓碑、自动触发、附件与阅读资料协议、历史保留。历史清理需独立设计与授权，不在首次迁移自动执行。

这是一条独立于插件 R1～R6 的工作线。复用保存/恢复边界，但不让外部备份格式改造阻塞首个内置插件宿主，也不因插件试点而放松共享数据安全。

## v2 更新：采纳范围与修正

新版最有价值的调整是降低立即换格式的紧迫性，把测量、同步元数据、编码、并发发布和删除语义分开。采纳“阶段 A 先补强，阶段 B 按证据决定”的实施方式，但不是一次开启所有新行为。

| v2 建议 | 采用方式或修正 |
| --- | --- |
| 小规模继续使用快照 | 采纳。正文统计不是完整请求体；补实际导出、图片展开、base64/JSON 编码时间和手机内存，不能以 50 MiB 文件警告线推算应用余量 |
| 同步元数据独立保存 | 采纳。先定义仓库/分支/根路径/协议版本的命名空间及迁移，逐实体记录已接受基线与忽略项。储存可用 IDB store 或 SQLite 表，但不先为各平台创建内容不一致的表 |
| 所有字符串 NFC、统一换行 | 不采纳通用改写。正文、代码、Markdown、密文字符串原样保留；路径规范化与碰撞单独处理。规范化只作用于明确的字段投影，不改正文来获得相同哈希 |
| 三端各写一个编码器 | Web/Tauri 优先共用 TS 编码器；Flutter 使用共享向量对拍，原生导出/import 仍需往返验证。不是必须额外实现 Rust 同步编码器 |
| 基线 ID 集合即可推断删除 | 仅在完整且已接受的同一命名空间快照之间成立。忽略/冲突项、首次还原、丢失基线、下载失败、不支持字段或旧客户端漏项不能当作删除；暂不默认传播 |
| 删除冲突默认恢复或重新上传 | 保留双方内容是合理目标，但不能自动复活原 ID 并覆盖删除意图。冲突记录保留删除和修改两种事实，用户选择恢复、保留删除并留副本，或另存；回收站同 ID 恢复也需校验内容 |
| 删除阈值 max(5, 10%) | 可作为批量确认的附加安全阀，不能替代完整性或权限检查；所有传播删除首版先预览并确认，小批量也不静默应用。百分比的取整、分母及边界需固定测试 |
| 按文档文件平铺 | 可作为试点布局；历史 ID 并非一定是 UUID，需要稳定安全映射。不设置 800 篇自动重排，先利用 Trees 完整遍历，避免布局迁移本身增加兼容风险 |
| 元数据逐字段合并 | 有条件采纳为后续批次。先定义关联组与未知字段策略，路径/保护/密钥与正文/源码/位置映射不允许独立拼接；保护元数据冲突阻止自动应用 |
| 内嵌图片外置 | 本机有明确收益，列为独立资源协议。需要原引用往返、哈希与大小校验、离线缓存、缺失资源、共享引用和保护边界；不在现有快照中简单换成本机 URL |
| 加密历史不可变文件 | 有条件采纳。加密历史可能随密码轮换重新加密，也可能被删除；同一 verId 不能无条件覆盖。可用版本 ID 加内容摘要或不可变对象映射，清理与保留另行设计 |
| 快照与指针原子性 | 采纳。可先评估以 Git Data API 在同一提交中创建快照并更新指针，保留旧路径和 JSON；这是独立于每文档布局的阶段 A 候选，不必等格式迁移 |
| 三次写请求、不到一分钟还原 | 仅是特定路径估算。有独立 blob 时请求更多；冷启动/保护历史/附件/重试都会改变请求数，限流上限不是吞吐保证，需测实际延迟并有界并发 |
| 分两到三批迁移后删旧格式 | 不按篇数或固定批次承诺。按字节预算准备对象，一次发布完整 manifest；保留旧快照并禁止不兼容客户端向新格式写入，不能为省空间立即删旧入口 |

`settings.json` 和 `templates.json` 也需要实体基线与冲突策略，不能只解决正文比较再整份覆盖。设备本地的凭证、插件授权/启用状态、恢复日志和同步基线不进入远端设置。

同步哈希与语义比较应分开：传输哈希检测存储字节是否变化，逻辑比较明确哪些字段构成用户修改；`exported_at`、本地搜索派生字段、同步确认时间不应制造用户冲突。不能通过剔除未知字段来获得稳定哈希却在还原时丢失它们。

## 对 v2 第 13 节八项问题的回复

| # | 确认结果与决定 |
| --- | --- |
| 1 快照及指针 | 每次 Push 创建新的版本化 JSON，版本为 UTC 毫秒时间标识；latest 是仅含版本标识的文本文件，不是 commit SHA/JSON manifest。代码先写快照，再按之前读到的指针 SHA 更新 latest；第二步失败可能留下孤立快照。409 等错误会退出本次任务，没有自动重新比较重试。基线只在两步均成功后记录。见 `src/lib/sync/github.ts` 的 pushToGitHub、putRemote |
| 2 仓库大小及次数 | 尚未测得实际备份仓库大小及历史发布次数，不能用 Nine Rings 源码仓库代替。后续在明确备份仓库与分支后只读统计：已发布快照、孤立快照、成功发布次数及时间跨度；仓库 size 是粗粒度汇总，单个当前值除以次数不足以证明增长速度，需多时点差值。Git 历史对象体积与当前文件总大小分开，gzip 影响也应测量而非绝对禁用 |
| 3 完整导出构成 | 本机只读聚合见下表。保护历史仅约 23.1 KiB 正文，现阶段不是主要体积来源；普通历史约 9.96 MiB 正文不进入快照。已测原生文档记录紧凑重建投影约 13.52 MiB，但并非真实完整导出：尚缺运行时设置/前端白名单/图片展开和 pretty JSON，需要通过实际导出入口统计。不得把 10.29 MiB 正文总量当作请求体 |
| 4 大文档内容 | 最大一篇 content JSON 为 3,544,036 B，其中一个 data URI 为 3,543,147 B（约 99.97%），文本 insert 仅 597 B；外置图片会显著缩小这份文档。第二篇 553,300 B、第三篇 524,042 B 没有 data URI，文本 insert 分别 348,862/331,521 B，不能靠图片拆分解决 |
| 5 使用模式 | 用户确认所有可构建版本都可能 Push/Pull，可能并发编辑同一文档，暂不需要自动同步。保持手动操作；并发三方合并与未知字段/保护能力拒写优先。Flutter 当前没有与 Web/Tauri 等价的安全三方 Pull 且不支持加密工作区，不能让它在同一共享空间中无提示覆盖新版内容；能力不足时拒写并提示，不为本次评估安装 Flutter 工具 |
| 6 基线粒度 | 本机保存 lastPullVersion/lastPushVersion，选择最近标识并下载那份完整快照作共同基线，再逐文档做规范化内容比较。远端基线快照含文档 ID，但本地未维护独立的逐文档 baseHash/ID 集合表，也未按忽略/冲突项分别确认。它足以做现有安全合并，不足以直接开启 v2 的删除表格；不能以最新看到的指针代替逐实体已接受状态 |
| 7 本地密文 | 是。content.encrypted 包含已有密文与随机 IV，存储及备份保留密文；Push 不为未编辑文档重新加密。本机有 1 篇有效加密文档和 2 条可导出的加密历史。哈希取确定性编码后的存储形态，无需解锁、不上传明文指纹；密码轮换可造成真实传输变化，加密历史也不能假定终身不改 |
| 8 保护文档远端删除 | 建议首版不自动删除受保护或只读文档：列为冲突，保留现有内容；用户解锁并明确确认后才执行软删除。密码保护意味着机密性/访问权限，并非绝对禁止本人删除，不能永远拒绝用户授权的删除。保护路径配置/密钥分组缺失或变化也不表示整组文档被授权删除 |

## 按 v2 修订后的推进方式

1. **继续 I0**：增加真实导出聚合诊断，区分持久化正文、文档记录、派生搜索文本、内嵌图片、保护历史、模板、可备份设置及请求体；另测实际备份仓库增长。不上传统计中的私有内容。
2. **先做兼容门禁与 I1**：所有参与 Push/Pull 的平台使用共享向量，确定正文/未知字段/加密/路径关联组；为能力不足客户端设计明确拒写。独立同步元数据保存已接受实体基线，不依附可还原配置。
3. **现有格式补强**：发布与本地确认的恢复日志、超时结果不明的只读确认、有界竞争处理；评估同提交快照加指针的可兼容实现。无变化时跳过新发布需要排除导出时间等易变字段，并核对上传期间的新编辑未被误确认。
4. **删除语义单独试点**：先生成不写入的三方计划，验证完整/缺失/忽略/重置/同 ID 回收站/保护项/修改对删除。缺少共同基线时只合并；首版传播需显式开启和确认，不随普通 Push/Pull 默认生效。
5. **阶段 B 保持候选**：按实际传输耗时、手机峰值内存、仓库增长和多端安全需求决定；小规模 REST 与平铺均可用，不保证迁移时间。附件协议和每文档布局可分开验收，但保护资源不能外置明文。

自动同步暂不实施。I0～I5 未完成，本文不将设计采纳标记为已实现功能，也不改变插件门禁顺序。
