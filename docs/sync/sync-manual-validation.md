# macOS Tauri / Web 手动同步验证流程

更新：2026-10-17。两端均使用 `132c64d` 或更新提交（0.3.0）；后续性能修复不会改变本流程。以下是用户真机验证步骤，不是已完成的验收记录。

> 已看到“首次迁移已完成”的客户端，从第 3 节继续；不要重复执行首次迁移。

## 准备

- A 为 macOS Tauri，B 为 Chrome 普通网页。两端核对设置中的实际构建号，均支持当前同步协议；其它未升级客户端停止使用这个备份连接。
- 两端分别导出当前完整 JSON 并保存到本机。你已有的备份继续保留；首次迁移界面仍需选择文件进行内容核验，如果内容已经变化，重新导出当前备份。
- 两端配置相同 owner/repo/path：`erocpil/nine-rings-backup` / `nine-rings-030.json`。Token 只在应用中输入，不放进反馈日志。
- 不执行旧格式“全量覆盖”代替下面的增量步骤。测试文档统一放在专用测试路径，保留现有文档。
- 准备记录表：客户端构建号、操作起止时间、阶段、读取次数/字节、提示、成功后的远端版本。错误时复制调试日志，隐藏 Token 等凭据。

## 实体名称说明

- 文档：按标题/路径识别。
- 界面与阅读偏好（旧显示 settings · frontend）：分栏、阅读位置、收藏/最近记录等一组可备份前端偏好，不是文件；选择远端会应用整组设置。
- 应用配置（settings · app-config）：另一组应用设置；同样按整组选择。
- 不希望在测试中改变本机偏好时，可以对设置实体选择忽略。没有基线不表示远端损坏或文件丢失。

## 1. 只读候选审查与取消

1. A 点击“预检实体差异”，记录各阶段与耗时。首次旧格式审查可能分批，批次应自动继续，累计读取数继续增长。
2. 点击“取消检查”，界面应立即恢复可操作；取消不修改正文或接受基线，不应在后台继续开始下一批。当前已经发出的 GET 可能仍需结束。
3. 再次预检，应复用已经核验的历史证据并最终展示候选，不能显示“需要完整的固定修订预检”。
4. 核对差异；若两端内容原本相同，预期实体相同。勾选“显示相同”等控件以查看隐藏项。预检本身不产生远端提交。

## 2. 首次迁移（只在一端执行一次）

1. 在 A 审查所有差异；有差异时明确选择本机、远端或忽略，必要时打开对比，然后“校验并保存选择”。未选差异不会自动采用本机覆盖远端。
2. 点击“导出迁移前本地备份”，保存后通过“选择已保存的备份进行核验”选择当前文件，看到“备份已核验”。过期文件被拒绝时重新导出，不修改 JSON 绕过核验。
3. 确认所有参与客户端支持协议，最低版本填写两端实际共同支持的版本（本次至少 0.3.0），勾选切换此备份连接的确认。
4. 点击“首次迁移并发布”，等明确完成提示。全相同时也会创建首次协议检查点；不因看不到差异就跳过迁移。
5. 成功后重新预检，确认进入增量模式。记录远端新版本；不要手动删除协议文件或修改 latest。

## 3. 第二端建立接受基线

1. B 重新预检。若全部相同，点击“确认相同内容”；这一步只确认本机基线，不应产生无意义的远端发布。
2. 有远端差异时逐项选择远端，保存选择后点击“应用所选远端实体”。未选中的本机内容应保留。
3. 成功后再次预检，确认已处理项变为相同；刷新 B，确认正文仍在、位置/应用状态正常。

## 4. A → B 单向往返

1. A 新建一份测试文档，正文包含中文、行内代码、列表和代码块。记录唯一测试标记。
2. A 预检、选择该本机实体、保存选择，并按界面要求核验当前本地备份后“发布所选本机实体”。
3. B 预检，选择该远端实体，保存选择并“应用所选远端实体”。检查标题、路径、格式与标记，刷新后再次检查。
4. 两端重新预检/确认相同内容，确保双方对这份文档建立相同基线。

## 5. B → A 与独立编辑

1. B 修改测试文档，发布；A 预检并应用远端变化，检查刷新/重启后仍保留。
2. 完成基线确认后，A 修改测试文档甲，B 修改另一份测试文档乙。
3. A 先发布；B 重新预检，甲选远端、乙选本机，先按界面分别应用/发布并在每次成功后重新预检。不要复用已经失效的选择。
4. A 拉取乙；两份修改都应保留，未选择的其它文档不变。

## 6. 同文档冲突

1. 先确认 A、B 对测试文档拥有相同基线，再分别改为不同文本。
2. A 先发布；B 重新预检，应显示双方修改/冲突，而不是静默覆盖。
3. B 打开比较，明确选择来源；若需要保留两份内容，先另存为测试文档或手动合并，再重新预检，不能假设逐实体同步会自动进行段内合并。
4. 发布/应用后在 A 再次核对最终结果。已有旧格式安全合并的“冲突副本”与此处逐实体选择不是同一操作。

## 7. 过期选择、忽略与缺席

- 过期选择：B 预检并保存草稿后，A 再发布一个测试修改；B 使用旧选择时必须拒绝/要求重新预检，不能覆盖新 HEAD。
- 忽略：选择忽略一份差异并保存，重新打开设置后核对草稿恢复；不应改正文或悄悄确认接受。
- 缺席：只对另建且已备份的测试文档尝试删除；另一端预检不应自动删除对应本机文档。删除传播当前不在范围。

## 补充：代表性内容和资源边界

- 在新建测试文档中补充表格、脚注、数学公式、Mermaid/flow、书签和 /toc，往返后同时检查源码与渲染；保留有代表性的嵌套列表/引用和中文行内代码。
- 对现有只读及加密/保护文档，检查同步后状态仍保留、输入正确密码可打开。不要通过改动真实保护路径的密码制造故障；涉及保护关系的候选拒绝应记录并保留原数据。
- 内嵌且已随文档备份的图片可以验证往返显示；本机图片目录、PDF/EPUB 源文件等设备本地资源不属于自动跨端复制范围，不能把另一端不存在本机路径当作正文丢失。

## 8. 失败与恢复（可选进阶）

先完成正常往返，再在测试文档上操作。不要删除本机数据库或恢复日志来制造故障。

- 预检期间断网：应明确失败且可重新预检，不能改远端或本机正文。
- 发布期间断网/进程退出：若提示结果不明，恢复网络/重启后先执行发布恢复的只读核验；不要重复点击发布来猜测是否成功。
- PREPARED/OBJECTS_READY/REJECTED 可按界面二次确认取消后重新预检；UNKNOWN/PUBLISHING/CONFIRMING 不能绕过只读恢复。
- Pull 应用后确认丢失：使用应用恢复入口核对实际内容并补确认，不重复导入，也不要用全量覆盖代替恢复。
- 如果没有合适的故障注入条件，记录“未执行”，不要将正常操作通过算作异常恢复已验收。

## 完成标准及反馈

正常 A→B、B→A、双方独立编辑、同文档冲突和刷新/重启后保留均符合预期；过期选择被拒绝，未选择/忽略/缺席不造成删除。每端至少记录一次首次预检、缓存后重复预检和迁移后预检耗时。

发生失败时提供：构建号、A/B、步骤编号、是否代理、最后阶段/批次、请求数/字节、完整错误和脱敏调试日志；不发 Token、完整私有正文或未经处理的备份。Chrome 更新新标签页问题单独记录，不将它当作同步数据错误。
