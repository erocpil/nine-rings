# 备份恢复协调与中断检测

## 当前范围

应用全量 JSON 导入和 GitHub Pull 通过同一把 Web Lock 串行恢复。同源、共享存储分区、运行新版代码的窗口之间生效；不保证跨浏览器配置、独立原生进程或旧版本窗口互斥。

- JSON 导入先解析、校验，持锁后才修改数据和设置。
- GitHub Pull 从获取本地恢复快照之前开始持锁，覆盖远端下载、合并/覆盖和原有失败补偿流程；回滚复用同一恢复上下文，不释放后重新抢锁。
- 锁被占用时立即拒绝，不排队执行可能已经过时的导入意图，也不触发失败补偿。用户应等待当前恢复完成后重新预检。
- 空白远端文件、JSON/结构校验失败等写入前错误不回写本地快照，也不推进 Pull 版本。错误提示不回显损坏文件中的正文片段。
- 已经开始写入但尚未提交时，GitHub 保留原有的快照补偿机制；数据库提交成功后发生日志或通知失败，不再重放导入前的快照。提交标志在保存收尾日志之前设置，避免把日志错误当作数据库提交失败。
- 不用定时租约判断锁过期，避免后台暂停中的窗口恢复运行时与新操作重叠。窗口关闭后由浏览器释放锁。
- 浏览器缺少 Web Locks 或无法写入恢复记录时拒绝开始恢复，不静默退化为无锁写入。无 `window` 的存储契约测试环境不使用浏览器锁。

**恢复前仍须关闭其他编辑窗口。** 此锁只协调恢复操作，不阻止普通编辑、Push、阅读器保存进度等写入。单书 `*.reading.json` 恢复也未接入这把锁。

## 恢复记录

localStorage 的 `nr:backup-restore-journal:v1` 只保留最近一次操作的版本、随机 ID、来源、合并/覆盖模式、阶段和时间。没有正文、备份内容、Token、原始错误消息或可重放的事务数据；不是历史审计日志。

阶段包括准备、写入、失败补偿、收尾、完成、写入前失败、结果待检查和用户已确认。读取未完成记录时尝试取得同一把锁：拿不到表示仍在恢复，拿到表示此前操作已中断。其他窗口可通过存储事件得知变化；恢复中的状态每两秒重新检查一次，以识别窗口意外关闭后的锁释放。窗口重新获取焦点或从后台回到可见状态时也重新检查。

主界面显示中断/失败及其他窗口恢复中的提示，设置的“数据与导入”和“同步与备份”提供详情。正常完成的记录默认折叠，不重复占据连接状态提示区域。

## 中断后的处理

1. 暂停编辑，先导出当前本地数据，检查文档和设置。提示旁的“导出当前本地备份”复用全量 JSON 导出；导出检查副本期间持有恢复锁，不允许同时恢复或清理记录。导出成功、失败或取消均不改变恢复记录。该副本不包含 PDF/EPUB 阅读资料库，也不是多库一致性快照。
2. 在设置中确认已检查本地数据；损坏记录需明确确认后清理。确认会验证记录 ID，防止旧对话框确认新的恢复记录；恢复仍在进行时禁止清理。存储不可读或缺少锁支持不等于记录损坏，此时只提供重新检查，不允许通过清理日志绕过错误。
3. 根据检查结果决定是否重新预检并导入。系统不会在重启后自动重试或自动回滚。

确认记录**不修复、不重试、不回滚任何数据**。中断和“结果待检查”记录未经确认时禁止新恢复；只有确定尚未开始写入的失败允许重新预检。开始写入后的任何失败保守地要求检查，包括快照补偿已经返回成功的情况，不能仅凭补偿返回就宣称多库状态完全复原。若数据操作已执行、仅完成记录保存失败，则保留待检查状态并明确提示，不能把记日志失败误当成导入失败而重复覆盖数据。

## 后续边界

尚未实现跨 IndexedDB/SQLite/localStorage 的原子恢复、普通写入隔离、可重放恢复计划或崩溃后的自动补偿。GitHub 与应用全量 JSON 也仍不包含 PDF/EPUB 阅读资料库。本阶段是协调与检测基础，不能视作这些能力已经完成。
