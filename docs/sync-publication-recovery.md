# 候选发布记录与中断恢复

> 当前状态（2026-10-17）：Web/Tauri 0.3.0 已开放经过认证的手动同步，正式入口、限制与恢复规则见[同步指南](incremental-sync.md)。下文带日期的能力关闭及未接入记录保留为历史，不代表当前发布状态；Flutter 仍未开放。

2026-10-15。`publication-store.ts` / `publication-recovery.ts` 是新协议发布基础；**生产能力为 0，当前旧格式 Push 不创建这些记录，也不自动改用新发布协议**。

## 冻结计划与本机记录

独立设备数据库 `nine-rings-sync-state-v1` 保存 attempts、summaries、baselines，不改变主文档数据库 schema，不进入普通备份，也不保存 Token。summaries 只包含空间、阶段、时间和提交标识，启动不为检查状态而读取整份冻结正文。

准备计划前检查封装、实体、能力、固定远端证据、与实体摘要绑定的本机修订、备份确认和参与端确认；原始 `preparePublication` 只允许**空备份命名空间**的首次候选；非空旧快照和已开启空间通过独立 `prepareReviewedPublication` 接口准备，任何未完成计划仍拒绝另建计划。产品已提供迁移准备/确认和受门禁约束的操作入口；当前发行能力仍为 0。测试中的能力 1 是隔离的假设认证环境，不是发布版本承诺。

记录包含冻结快照、原始 SHA-256、控制文件、expectedParent、目标 snapshotId、本机存储代次，以及实际接受实体的哈希和必要元数据。当前只记录 present，不推断 absent 或删除；非空远端现通过下述冻结选择证据接入；旧记录仍按首次空空间规则验证。冻结记录（含接受数据）上限 128 MiB，持久化失败时不得开始写远端。

## 阶段与发布边界

| 阶段 | 含义 |
| --- | --- |
| PREPARED | 冻结意图已提交本机；外部对象准备器尚未获准更新引用 |
| OBJECTS_READY | 已核验候选 Git commit：单父项为 expectedParent，且仅修改快照、latest 和控制三个计划文件；字节必须与冻结记录相同 |
| PUBLISHING | 在唯一一次 PATCH 前以事务持久化；并发窗口通过记录 ID/阶段/commit 比较，只有一个能进入 |
| UNKNOWN | 响应丢失、超时或无法确认；禁止重放原 PATCH |
| REJECTED | 明确 HTTP 拒绝，接受基线不推进；需新的显式预检和计划，不自动 Pull |
| CONFIRMING | 已确认引用更新，等待本机接受记录提交 |
| COMPLETE | 冻结接受数据与完成标志在同一个本机事务中提交 |

恢复/发布确认复用文档恢复锁并检查存储代次。普通新编辑不被写回或覆盖；接受基线来自冻结计划，新编辑仍是后续待处理差异。若文档库已被恢复，旧发布不能被确认成新库的基线。本机确认失败保留 CONFIRMING，不把已发布数据回滚。

对象创建器已完成服务层接入，见下文；尚无正式 UI/生产 GitHub POST 入口。对象可能已创建却尚未发布，记录库不自动删除它们。`force:false` 仅为快进保护，不是严格 expected-HEAD CAS，也不能防止外部强推。

## 启动检测与只读恢复

启动只检查轻量本机摘要，有未完成记录时提示进入备份设置；不会自动使用凭据连接远端。设置中的「只读核实发布」是显式 GET-only 检查，凭据由用户当前配置提供，连接必须与记录一致。

先固定目标分支头 H；H 等于候选 commit，或 `GET /compare/<commit>...<H>` 返回 ahead 且 merge_base 为候选 commit，才能证明当前 H 包含本次发布。随后再次核验候选提交中的三个文件和父提交，再确认冻结基线。采用 [GitHub Compare API](https://docs.github.com/en/rest/commits/commits#compare-two-commits) 的明确方向。

403/404/超时、分叉、落后、错误合并基点及文件不一致均保留 UNKNOWN；不能据此认定“从未发布”。H 包含后续提交时，只接受本次冻结值，不将后续远端编辑也标记为已接受。已观察到异常的记录不提供“忽略后重发”快捷入口。

当前接受账本与主文档存储没有跨库事务承诺；已实现的是“发布确认账本与 COMPLETE”原子提交，尚非完整 Pull 应用日志。正式上线仍需非空远端规划、对象上传接入、Pull 接受状态及显式切换 UI。


## 首次发布的对象准备与保存边界（2026-10-16）

`preparePublicationFromSavedState` 先等待宿主保存屏障成功，再读取完整候选封装；之前确认的本地备份仍须与所得实体修订相同，不能用旧备份证明新内容。保存/导出失败或取消不创建 PREPARED；恢复代次在保存前捕获，导出后、内容验证后及写记录事务内再次核对，避免将恢复前的字节绑定到新文档库。宿主仍应按既有同步操作规则冻结编辑交互；本服务不承担界面锁定。

`publication-objects.ts` 为既有空命名空间首次发布提供可恢复对象准备器，只接受持久化 PREPARED，重启后重新执行封装/正文/能力校验。生产能力为 0 时，在任何 Git 请求前拒绝；测试中的开放能力仅在隔离模块 mock 中注入。凭据、GitHub transport 和真正的 POST 入口尚未接入产品，旧备份上传不调用此服务。

对象准备取得按空间命名的 Web Lock 后：

1. GET 核对当前分支 head 仍为 expectedParent，读取固定父提交；确认目标快照、latest 和 control 不存在。
2. 创建三个 UTF-8 Blob，逐一比较 Git Blob SHA；以固定父树为 base_tree 创建仅含三条 `100644/blob` 路径的 Tree，再创建单父项 Commit。
3. 再次 GET 核对分支 head；通过既有 `recordPublicationObjects` GET 回读提交、树和 Blob，验证三个文件字节、唯一父提交及完整变更范围，之后以事务进入 OBJECTS_READY。
4. 后续显式调用既有 `publishRecordedCommit`，才可按 PUBLISHING → PATCH(force:false) → CONFIRMING → COMPLETE 发布和确认；对象准备器本身没有 PATCH 参数，不推进接受账本。

每次对象创建前后检查取消、恢复代次和轻量日志摘要；摘要只用于判断原计划是否仍活动，不替代首次完整记录验证。登记事务内再次检查取消与恢复。两个遵守同一锁的窗口不会重复执行对象创建；网络中的单次 POST 无法因取消而撤回，但取消后不登记或发布。准备中断、响应丢失、错误 SHA、非法提交或远端推进都保持 PREPARED，不自动重试或清理；用户重新执行准备可能产生额外不可达 Git 对象，但不会重复更新引用。PUBLISHING/UNKNOWN 继续禁止从对象准备入口重放。

首次空空间服务链路已完成；非空远端的后续接入见下一节，正式宿主传输/启用流程仍未开放。不能把远端选取、忽略、相等或待删除项目一并记为本机发布已接受。Pull 实际应用日志及相等证据确认仍独立推进。也尚未采用分片/对象化正文格式，现有快照 Blob 仍可能较大，不能据此宣称解决代理大请求限制。


## 非空远端的冻结发布意图（2026-10-16）

`reviewed-publication.ts` 接受已有 EntityReview、明确选择、备份/参与端确认和快照身份；先经过宿主保存屏障，再验证完整本机实体修订、当前接受基线和恢复代次。GET 重新执行远端协议预检，要求同一空间、同一 head、完整历史及原快照字节；不将缓存报告或选择草稿中的布尔值作为远端证明。远端读取后再次导出并核对本机，内容变化不创建 PREPARED。

| 远端状态 | 新快照 parent | control 文件 | Git 提交变更 |
| --- | --- | --- | --- |
| 非空旧格式首次切换 | null，成为协议链根 | 新建 firstSnapshot 指向本次快照 | 新快照、latest、control 三份 |
| 已启用且链完整 | 原快照 ID 与原始字节 SHA-256 | 保留原始字节，禁止重建或格式化 | 仅新快照与 latest 两份 |

已有快照身份禁止覆盖；与远端实体相同的候选不创建空提交，接受确认需要后续独立流程。旧格式仍须满足从未启用的历史与本机观察约束；已启用空间只在重新核验完整快照链和候选能力后使用本接口，不放开通用 bootstrap 的 join-required 规则。远端封装的读写能力声明同样必须被当前运行端支持，不能因可解析正文而忽略协议声明。正式能力保持 0，Flutter 不支持这些发布意图。

日志仍使用既有设备数据库和事务，新增可选 `reviewed` 证据：冻结的两侧来源、基线、输入绑定、选择、计划摘要、模式及候选实体修订。`localRevision` 保留原本机修订，与备份确认一致；`candidateRevision` 单独表示混合选择后的候选。128 MiB 日志预算仍适用，包含完整证据后过大的计划会拒绝，不意味着任意大备份已可发布。

确认接受的子集严格等于重新组装所得 `afterPublication`，而非所有 outgoing 实体。远端选择须等真正 Pull 应用成功；相等项须等独立等价确认；忽略、未解决冲突和 pending-delete 不推进。完成事务只写本次接受子集，未涉及的旧接受记录保持原样。重启时重新计算来源绑定、原本机修订、基线摘要、计划、候选与接受子集，并验证新快照父引用；回读 Git 提交时还核对原快照/指针证据及控制文件不变，拒绝计划外文件变更。

对象准备、唯一引用更新、UNKNOWN 只读恢复和确认事务沿用既有链路；测试通过模拟 Git API 验证两种模式创建对象至发布响应丢失后的恢复。本批没有产品按钮、生产传输调用、真实远端写入、Pull 应用或相等确认。下一步接入显式宿主传输/启用边界与 Pull 应用日志；未来 Pull 与发布接受必须继续共用恢复锁，并阻止未完成发布期间另建接受操作。


## 显式迁移与继续发布入口（2026-10-16）

设置中的候选审查已接本地备份文件核验、参与设备/最低版本及首次切换确认，宿主桥接见 `incremental-actions.ts`。旧格式无实体变化时，仅明确 `allowMigrationCheckpoint` 才可创建首次检查点；证据记为 checkpoint，仅限 legacy-switch，重启重新组装核验。检查点不确认相等/远端选择、不导入正文；已启用空间仍拒绝无变化发布。正式能力为 0 时不创建意图或发送对象/引用写入。

未完成 PREPARED/OBJECTS_READY 可经“继续已确认的冻结发布”恢复对象准备并发布原冻结提交；先等待保存，使用当前配置匹配原连接。PUBLISHING/UNKNOWN 只允许原 GET-only 核实，拒绝从继续入口重发；该规则也在宿主服务检查，不依赖按钮隐藏。引用更新前先保存连接防降级状态；完成发布后若观察状态失败，报告“发布与接受已完成，仍需重新预检”，不诱导重复上传。
