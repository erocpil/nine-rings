# 选择性 Pull、应用日志与相等确认

2026-10-16。服务层基础已实现；生产协议读写能力仍为 0，没有新的产品操作按钮或真实远端写入。旧 Push/Pull 保持原行为。

## 只应用明确选择的远端实体

`planReviewedPull` 以完整冻结本机快照为基础，只替换 `afterLocalApply` 中明确选择的远端实体。本机新增、未选择、忽略、未解决冲突与缺席的实体均保留；缺席不表示删除。正文、属性、模板、设置与保护实体仍各自遵守已认证整实体契约，组合后的完整保护关系和正文必须再次认证。派生搜索文本不作为接受依据。

写入采用宿主的 **merge** 导入，禁止 replace，避免删除未导出的普通历史、回收站等本机数据。目标快照上限 64 MiB，含两侧来源与选择的本机日志上限 128 MiB；不做静默裁剪。正文数据库与接受日志之间没有跨库原子性承诺。

## 应用顺序与互斥

`applyReviewedPull` 复用 `withBackupRestore` 的恢复锁与上下文：宿主进入同步忙碌状态，等待保存屏障，再导出当前本机，核对选择绑定、实体修订、基线与恢复代次。远端封装必须受运行端能力支持；GET 核对当前分支 head 与固定快照字节。网络读取后再次导出/核对本机，拒绝检查期间发生的新编辑。

独立设备日志仍用 `nine-rings-sync-state-v1` 数据库，内部 schema 升为 2，以保留现有 attempts/summaries/baselines 的迁移方式增加 pulls/pullSummaries。发布准备与 Pull 准备的事务均读取对方轻量摘要，任何空间有未完成操作时禁止另建冲突意图；应用过程另由恢复锁跨窗口串行。旧版本直接打开 version 1 的日志库会失败，不能绕过升级或清空日志。

| 阶段 | 含义 |
| --- | --- |
| PREPARED | 完整目标、两侧证据及选择已持久保存，尚未导入 |
| APPLYING | 恢复上下文已分配应用代次，导入结果可能未知 |
| CONFIRMING | 实际完整导出已与目标实体修订匹配，等待接受事务 |
| COMPLETE | 选择的远端接受子集与完成标志在同一 IDB 事务中提交 |
| ABORTED | 应用开始前失败，可重新预检；不推断已应用 |

实际导出必须与完整目标的实体修订一致，才可确认接受。仅存储返回成功不够；导出失败、内容不匹配、取消或文档库再次恢复均不确认。接受子集不包含未选择、忽略、相等或本机发布项，未涉及的旧基线保持原样。普通新编辑不是回滚理由。

## 中断恢复

`recoverReviewedPull` 只在恢复锁内读取实际本机并核对冻结计划，不再次导入，不自动回滚。实际目标已存在且应用代次未被再次替换时，可完成接受事务；失败的接受事务可重试确认，正文不重放。部分应用、原始内容或后来编辑与完整目标不一致时保留待检查状态，不能猜测哪一部分已成功。

通用备份恢复日志仍会对中断标记 needs-review；接受日志恢复不会擅自清除这个提示。后续产品恢复界面须把二者对照展示，只能确认属于同一恢复代次的记录，不能顺带清除其它恢复提示。启动轻量 Pull 状态和用户检查/终止界面尚待接入；未完成记录不能通过简单重试导入来跳过。

## 相同内容的独立接受

`confirmEqualReviewedEntities` 共用日志与接受事务，mode 为 equal。保存后验证两侧、当前本机、基线、固定远端及能力，只取规划中的 `equal` 实体；不调用导入，不修改文档库代次，不创建 Git 对象。与本机或远端不同的实体、被忽略的相等项以及缺席项都不会借此确认。

确认前再次读取本机，随后通过 PREPARED → CONFIRMING → COMPLETE 冻结证据并提交接受子集。相等确认中断后，同样只核对实际本机，不执行数据导入。该路径也受生产能力为 0 的门禁，不是正式启用协议的替代入口。
