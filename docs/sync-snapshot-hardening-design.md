## 3. 兼容门禁与上线顺序

分清三个独立版本：现有导入/导出 `version`（当前接受 1/2）、未来同步封装 `format`、确定性编码 `codec`。应用版本和数据库 schema 版本均不能代替它们。

未来封装的概念字段如下，数值仅为示意，不是已发布格式：

```json
{
  "header": {
    "kind": "nine-rings.sync-snapshot",
    "format": 1,
    "codec": 1,
    "requires": {
      "read": 1,
      "write": 1,
      "readFeatures": [],
      "writeFeatures": []
    },
    "id": "<UTC时间>-<设备短码>-<随机后缀>",
    "parent": { "id": "<上一发布身份>", "sha256": "<上一快照摘要>" },
    "createdAt": "<UTC时间>",
    "writtenBy": { "app": "<版本>", "platform": "<平台>", "deviceId": "<随机设备身份>" }
  }
}
```

读写等级及必需特性集合均须满足；未知的必需特性不能仅凭等级较高就忽略。可另有展示用途的 features 标签，但不得混同安全门禁。继承远端的最低读写等级与特性要求，不因某端未识别字段、当前文档未使用某功能而自动降级；降级只能是明确的格式转换。

“能渲染”“能原样存储/再导出”“能编辑后保留未知数据”“能三方合并”分别验收。Web/Tauri 共享 TS 不代表 Rust 存储往返无损；Flutter 仍需覆盖扩展 Delta、路径/类型/概念、保护数据、模板、未知字段和导出白名单。受限客户端拒写；是否允许只读导入也须满足读取能力。Flutter 插件架构及本地工具安装不在本轮范围。

按 v4.1，本轮**暂不支持旧客户端**：先完整导出，再升级全部参与设备并核实最低受支持版本，之后显式开启新协议写入；隔离仓库/空间和旧版本行为适配不作为首批交付。源码外部稿件写有“已确认所有设备可升级”，这里只将其作为上线前提，不据此把实际升级验收标记完成。

**旧二进制不会自行学会检查 header**。不支持旧端是一项运行前提，不是阻止它写入的技术保证；受支持客户端检测到缺头、身份不符、无法验证的父链或能力不符时，暂停应用和推送，保留差异查看及显式恢复入口，不把异常唯一归因为旧端。受支持版本之间继续先读后写并执行能力门禁。首次设备/本机基线清空不意味着远端仍处于切换前，具体初始化与降级规则见第 10 节。

## 4. 已接受实体基线与事务

未来逻辑记录（不是本批数据库迁移）：

| 记录 | 关键字段 |
| --- | --- |
| space | GitHub 主机、owner/repo、显式分支、根路径、format/codec；空间身份变化不复用旧基线 |
| entity baseline | space、entityType、entityId、baseHash、baseMeta、acceptedSnapshot、present/absent 与接受状态；必要时保留基线正文对象定位 |
| sync state | 最近观察到的远端发布、全部确认范围、设备身份、协议开启状态；不以 seen 等同 accepted |
| attempt | 随机操作 ID、冻结快照身份/摘要、父指针和旧 SHA、预期提交、阶段、确认结果、候选孤立对象 |

这些记录不进入可还原的用户设置，不包含 Token、解锁密钥或明文保护内容。文档、模板、可同步设置、保护元数据及保护历史均要声明实体身份；不能只给 notes 建基线而整份覆盖其他内容。

正文整体冲突判定可以仅保存基线正文哈希，元数据字段合并另存 baseMeta；这能避免常规比较下载完整旧快照。若要提供基于原文的 diff3/冲突展示，则需可获取的基线正文，不能从哈希恢复。正文/源码/书签/引用位置为关联组，路径/保护/密钥标识为关联组；未知元数据也要有保留和比较策略。

Pull 只确认实际接受的实体，忽略、跳过或待解决项保留原基线。文档与基线在同一 IDB/SQLite 事务内更新；涉及模板或 localStorage 时使用可恢复计划与幂等确认，不能声称一个事务覆盖全部存储。上传基线对应**冻结时的内容与修订**；网络期间的新编辑继续为待同步，不能随着成功通知一起清零。

首次升级可下载已接受版本一次建立基线；版本已丢失、空间不符或来源不明时，降级为保守合并，不初始化删除资格。远端成功、本机基线确认失败时记录“远端已发布、本机待确认”，启动后只读核实，不误称上传失败后再写一次。

## 5. 发布协议与不确定结果

保留用户触发的预检和明确 Pull。发现新远端版本，默认阻止当前 Push 并引导安全合并；可在未来提供显式的“合并后重试”，不默认导入远端数据。候选上限三轮只表示有界**重新比较与生成计划**，不代表对 POST/PATCH/PUT 自动原样重放；403/429、校验错误和网络超时也不能一概视作竞争。

推荐顺序：

1. 保存并冻结本地快照、修订与目标空间；读取固定远端 HEAD、指针和能力头。
2. 校验能力及差异计划。无本地逻辑变化且远端已被接受时跳过发布；导出时间、设备显示名、派生搜索字段不制造变化。远端有更新不能误报“已同步”。
3. 在本机生成不可变资产及快照，**先持久化 attempt，再发送首个远端写请求**；身份包含随机后缀并绑定字节摘要，不仅靠毫秒时间避免冲突。
4. 优先试验**一个 tree/commit 同时添加快照并更新原路径文本 latest**。保留原 tree 与父提交，非强制推进分支。保留现有 JSON/文本指针的容器与路径，消除新发布器“两提交之间”的可见窗口；这不是对旧客户端读写新协议的支持承诺，空仓库初始化单独验收。
5. 确认发布结果后确认本机基线；记录与清理分离。

当前 `c2f790a` 仍是快照提交后单独 Contents PUT latest，尚未实现第 4 步。混用旧发布器时，即使新发布器采用同提交，旧代码仍可能独立创建孤立文件；不能宣称整个仓库已获得统一的原子发布协议。`force:false` 约束快进，不是任意条件下严格 expected-HEAD CAS；Contents 旧 SHA 也只约束那个文件，不是整个仓库事务。[Git 引用接口](https://docs.github.com/en/rest/git/refs#update-a-reference)

| 结果 | 处理 |
| --- | --- |
| 明确 HTTP 拒绝 | 停止，保留具体阶段；只有确认属于并发且用户允许时才重新比较 |
| 快照/Blob 成功，指针未发布 | 不记录成功；对象可供后续验证复用，不能仅按文件存在发布 |
| 发布响应丢失或取消 | 只读取得当前指针及提交/摘要，确认本次是否已发布，禁止盲重放 |
| 指针已被后续设备推进 | 检查已记录提交与父链是否证明本次曾成功，不把“现在不指向我”直接当成未成功 |
| 状态无法证实 | 保留待检查，允许导出检查，不自动回滚远端或覆盖本机 |

新 JSON 指针若包含 id/parent/sha256/size，应作为另一次协议升级；不能让现有仅执行 `trim()` 的读取器把整段 JSON 当版本号。完整性摘要不等于签名，也不证明仓库写入方可信。

## 6. 删除、资产和历史回收

删除推断同时要求：同一空间和协议、完整快照声明及全部实体可读、已接受基线、无被忽略/未解决项、已声明该实体种类和覆盖范围、不存在旧客户端漏导。回收站不入当前备份只是现状，不能单凭远端缺少 ID 就授权删除。完整性/能力不满足、远端空白/损坏、新设备或基线重置时只保守合并。

基线推断可以用于完整快照内的已知删除，不强制给所有情形都加墓碑；但离线设备、跨保留窗口、部分同步或按实体增量布局仍需删除代次/墓碑及期限协议。初版仅预览并显式确认，全部远端删除只软删除；受保护/只读文档先冲突，解锁并授权后处理。修改对删除保留两种意图，不自动复活原 ID。`max(5, ceil(0.1 × N))` 可作为额外的批量提醒线，N 为应用计划前本机有效文档数；超过才触发额外确认，不替代任意一条删除的完整性与授权检查。

图片仅在同步投影层外置，本地模型维持原样。64 KiB 只是候选阈值，先量实际完整导出。限定已知图片槽位，不能递归替换任意正文字符串；以类型化引用和能力头避免与用户内容碰撞。校验原始 URI 的 MIME、参数、base64 字母表/填充及字节预算；重编码无法逐字节还原时保留内联，必要时保存原始前缀/表达。规范化 URI 不能悄悄改变正文或其哈希。

资产按内容摘要寻址，下载后核对摘要、长度与 MIME，限制单对象/累计体积。全体必需资产准备并校验后才应用文档；缺失不写成空图或“无该文档”。模板同样受约束。不得从密文提取明文图片；新保护资源协议未就绪时维持完整密文同步，保护范围不同的资产也不能仅因明文字节相同就跨域复用。普通文件夹图片分栏与 PDF/EPUB 原件不因该协议自动进入备份。

保留资源按**所有保留快照、基线、手工检查点及待确认发布**的引用闭包决定；parent 链不可达或超过 24 小时只形成候选，不是删除授权。本机 pending_orphans 不证明其他设备未引用该对象。删除远端文件不等于回收 Git 历史；保留的分支/标签仍可使对象可达，服务端回收时间也不由应用控制。

无父提交加强制更新引用属于独立维护操作，不进入普通 Push、启动修复或自动定时任务。必须单独明确授权、导出回退、核实所有写入方暂停、固定旧 HEAD/保留集合/资产闭包并验证新树。老客户端不认识维护锁或代次时，不能靠一个 JSON 标记保证互斥；不能承诺“只使用路径所以重写历史一定安全”。

## 7. 测量脚本评估与后续工具契约

附件脚本只读 GET，未读取正文，但会输出 owner/repo、分支、文件路径及最大文件清单，并非“只输出统计数字”。本次仅静态审查，没有用其读取真实备份仓库、取得运行中应用令牌，也没有将原脚本直接放入 scripts。

| 脚本现状 | 纳入仓库前需调整 |
| --- | --- |
| 仓库 size / 提交数推算每提交打包体积及年增长 | 删除该因果推断。size 是延迟汇总，不保证是仅此分支的精确 pack 大小；Git 压缩、其他引用与非备份提交会干扰。至少记录同口径多时点差值，分开报告当前未压缩文件量、服务端 size 与成功发布次数 |
| 按一次 Push 两次 commit 换算 | 不固定；空仓库、大快照与未来同提交协议都可能不同，提交总数也不等于成功发布次数 |
| 提交分页只显示不完整提示 | JSON 同时声明覆盖窗口与 lowerBound；未覆盖完整近 90 天时不得输出精确的 90 天节奏。采样起点不能叫仓库首次提交 |
| 递归树截断后仍汇总/投影 | 完整遍历非递归子树或明确返回不完整且停用相关判断；截断不是缺少/已删除 |
| 时间与参数 | 校验仓库/分支、页数上限、正则及日期，过滤未来时间；明确空仓库与无权限，加入请求超时和预算 |
| `GITHUB_API_URL` 任意覆盖 | 发布工具固定 api.github.com；模拟服务器仅显式测试模式且禁止带真实令牌，禁止跨源重定向携带凭据；Token 仅取显式环境变量，不从桌面配置/日志自动提取 |
| 默认展示最大文件路径 | 默认脱敏聚合，详细路径需显式选项；报告不含正文、认证头和完整错误响应 |

下一批 I0 工具应提供离线 fixture 模式和真实只读模式，先验证空仓库、多页、截断、限流、过时/未来时间及参数错误，再对明确目标仓库取样。现已按此契约实现只读工具并对用户指定备份仓库取样；结果及未测边界见[测量说明](backup-measurement.md)，不能用源码仓库代替备份仓库。经验性的 500 MiB/三年阈值只是产品候选，不能据此直接重写历史。

运行时导出统计另分正文、记录元数据、search_text、内嵌资源、模板、保护历史、设置及最终 UTF-8/Base64 请求字节；只汇总数量/大小。既有 203 篇统计保留为日期样本，新 783 篇日志只证明完整导出及失败请求大小，无法补出图片分布、仓库增长或未来降幅。

## 10. v4.1 更新：实施契约与验收修正

参考 `~/Downloads/sync-incremental-design (4).md`。采用其六步实施框架、意图先落盘、present/absent 基线、哨兵脱敏测试、故障点矩阵及事先记录决策阈值。D1 本轮不支持旧客户端，停止扩展首批隔离方案；D4 采用为**启动评估的触发线**，不自动执行格式迁移、删除或历史重写。以下修正优先于原稿的绝对化表述。

### 10.1 切换与协议异常

- 本轮切换条件：先取得可验证的完整导出，全部参与设备升级到实际发布的最低受支持版本，再开启新写入。最低版本号在实现与验收后填写，不先杜撰；应用版本门槛与 read/write 能力等级分开。
- 加性 header 的快照身份必须等于文本 latest 的版本标记；本设计使用 header.id，原稿的 header.version 表示同一含义，最终 schema 只选一个，避免与顶层 JSON version 混淆。parent 是快照身份关系，expectedParent 则是 Git 提交 SHA，两者不互换。
- 缺头、身份不匹配或父链无法验证均为“协议/完整性异常”，可能来自旧写入、人工修改、损坏、授权不足或历史清理；不直接断定为旧客户端。即使头完整，也不能证明所有新字段未被旧写入方丢弃；头部不是签名或完整的写入者证明。
- **本机没有基线不能作为无头例外的充分条件。** 新设备、清空存储或更换浏览器后也没有基线。读取远端控制状态与可验证历史，能证明尚未切换时才允许显式接入旧快照；无法证明时提供只读预检与手动迁移，不自动信任或报警后自动恢复。
- 远端协议开启状态作为受支持客户端的控制信息随发布维护，本机保留已观察到的开启事实；它们是异常检测辅助，不是本轮额外建设的一套多代协议，也不能阻止持有写权限的旧程序改写。
- 父链核验沿用本机已验证检查点并设读取预算。祖先缺失/截断/无权限与明确矛盾分开，不能把链检查失败当成历史不存在；保留/压缩前须先定义检查点和迁移规则。
- 异常时只读差异预检不修改正文、基线和远端发布；诊断日志可以更新。恢复首先是只读预览，真正回退远端必须明确确认，创建新的非强制发布并保留当前快照，不回拨分支或自动强推。“以当前内容继续”须通过格式、能力、资产和并发校验，不能靠一次确认跳过损坏或不支持的格式。

### 10.2 编码与实体确认

字符串值保持原样，仅规范 JSON 结构；实体语义哈希与完整快照字节摘要分开。数字规则需明确 JS/Dart 都能无损处理的范围，不能静默舍入超出安全整数范围的未知字段；孤立代理项使用明确的 JSON 转义策略，避免 UTF-8 编码将其替换成 U+FFFD。测试以冻结输入/时钟为前提区分编码稳定性与每次导出元信息变化，不能要求动态导出时间不同的完整文件仍逐字节相同。

present/absent 是基线的存在性，不是删除授权；include/ignore/conflict/pending-delete 是计划决定，不是基线状态。未知、尚未接受、明确缺席分别表示。受保护路径、保护历史也须纳入实体范围。基线在成功 Push 后按冻结内容确认，在 Pull 时按实际应用结果确认，不限于发布状态机的一条路径。

文档与同库基线可以采用一个事务；当前模板/前端设置位于 localStorage，不能把“一个 setting 一个实体”推导成它们已能与 SQLite/IDB 一起提交。首版采用实体应用日志和可恢复确认，或另行迁移存储；没有跨库原子性的证据就不承诺任意中断后完全无半恢复。

### 10.3 发布内容必须来自已核实的远端与本机计划

采纳“本机明确接受的修改覆盖在当前远端之上”，不用本机完整导出覆盖未接受的远端项。计划必须同时声明最终字节来源和是否确认本机基线：

| 计划结果 | 新快照来源 | 本机基线 |
| --- | --- | --- |
| 明确选择本地修改 | 冻结本机字节 | 发布确认后接受冻结值 |
| 明确接受远端 | 已核实远端字节 | 本机实际应用并确认后接受 |
| 忽略/未解决冲突/待确认删除 | 保留已核实的远端字节或明确缺席 | 保持原基线；本机独有草稿不丢弃 |
| 双方相同 | 已验证相同的规范内容 | 可按确认规则收敛；不为此强制发布 |
| 已确认删除（未来特性） | 按删除计划移除 | 确认后记录 absent |

“本地与基线相同”并不等于“本地与远端相同”。若远端指针已前进，当前全量格式没有独立实体索引，通常需下载固定提交上的远端快照后才能得出计划；不能先声称没有忽略/冲突，再以此省略识别它们所需的下载。缓存必须绑定具体提交/快照摘要，哈希与 baseMeta 不能重建被忽略项的远端正文。只有已核实远端未变、缓存有效且接受状态完整时才省略下载。

### 10.4 可恢复发布状态机

意图至少记录目标空间、intentId、expectedParent、snapshotId/摘要、冻结本机修订、**实际接受的实体哈希与必要元数据/存在性**、操作阶段与预期 commitSha；只记哈希不足以恢复 baseMeta。复用恢复协调的锁与代次约束，持久化发布意图另行实现，不把现有恢复记录误当可重放日志。

| 状态 | 持久化与下一步 |
| --- | --- |
| PREPARED | 首个远端写请求前落盘；本机快照已冻结，尚未允许更新引用 |
| OBJECTS_READY | 已记录完整快照、指针、资产所需对象及 commitSha；它们尚未作为本次发布推进分支 |
| PUBLISHING | **先落盘再调用 PATCH ref**；取消或结果丢失进入 UNKNOWN |
| CONFIRMING | 已确认发布，按意图中的冻结值确认基线；此状态补齐原稿状态表缺失的确认阶段 |
| COMPLETE | 本机接受状态和完成标志提交后才能清除/归档意图 |
| REJECTED | 明确拒绝，基线不变；保留诊断/对象信息，再由用户预检新计划，不直接自动 Pull |
| UNKNOWN | 结果不明，保留意图，只读核实；不可因一次查询失败清除 |

恢复先读固定分支头 H，再使用明确方向的 `GET /compare/<commitSha>...<H>`：H 与 commitSha 相同，或比较返回 ahead 且 merge_base_commit.sha 等于 commitSha、能证明 H 包含该提交，才按已发布确认，并核对该提交中的快照与指针对应本次意图。H 已包含后续发布时，确认本次成功不等于本机已接受最新远端。[Compare API](https://docs.github.com/en/rest/commits/commits#compare-two-commits)

Compare 的 404/403/超时、未知状态、历史改写或不可达提交保留 UNKNOWN，不能解释成“确认未发布”。分叉/落后也不能排除曾发布后被外部重写。只有当前发布状态、对象和父提交已核实时，才能显式构造新 intent 再发布；不重发原 PATCH，不承诺跨网络故障的 exactly-once。`force:false` 保留快进保护，不等于任意情况下的 expected-HEAD CAS。[引用更新](https://docs.github.com/en/rest/git/refs#update-a-reference)

“原子发布”只保证本次分支可见文件树一起出现，不是远端完全零副作用：预上传会产生暂时不可达的 blob/tree/commit，后续成功发布也可能使更早快照不再由当前 latest 直接引用。取消发生在引用前通常不推进发布，但对象仍可存在；本批不得自动删除。空仓库当前初始化会产生占位文件，未来需独立 bootstrap 规则与验收，不能把普通非空仓库的“两路径改动”断言直接套用。加入资产后发布集合也不再恰好两个路径，应断言只修改计划中的快照、指针、资产和必要控制路径，保留命名空间外内容。

### 10.5 决策阈值与测量口径

| 指标 | v4.1 建议触发线 | 采用口径 |
| --- | --- | --- |
| 最弱设备推送耗时 | >60 秒 | 记录保存/编码/校验/网络/确认的分段耗时与网络条件，区分一次异常与稳定表现 |
| 编码峰值内存 | >150 MiB 或可用预算的 20% | 标记进程/JS 堆/增量峰值及测量工具，不混合口径；不可测记 unknown，不能记 0 |
| 单请求体 | 失败量级的 50% | **待定**。36.4/45.5 MB 的失败不是失败阈值，直连成功也不能定位代理限制；需有效边界证据后才能填写 |
| 三年仓库增长 | >500 MiB | 优先用多时点同口径观察；2026-10-14 用户允许低活跃度阶段先用明确频率/边际增长假设的情景估算，不等待采样阻塞实施。假设与实测分列，只触发评估，不直接强制重写历史 |
| 外置后快照大小 | >25 MiB | 应用预算线，不由 Git 文件警告线推导出 REST 安全限额 |
| 自动同步需求 | 用户决定新增时 | 当前不实施；重新评估同步机制，不因这项候选自动加入后台同步 |

任一有效指标超线启动评估，不自动迁移；缺少最弱设备数据或内存不可测时不能宣布“全部满足，所以不做增量”。修改预算应记录日期、依据与基准，不为了回避结果事后移动阈值。六类大小统计采用互斥分类，嵌套图片不能既计入正文又计入图片后相加；JSON 包装、转义与未归类字节单列，所有实际字节必须能对账，而不是用小于 1% 的差值隐藏遗漏。

### 10.6 验收与实施节奏修正

保留原稿的哨兵脱敏、跨端向量、无变化零写入、发布中断、同 ID 回收站、受保护删除与资产损坏测试，并增加：

- 新设备加入已切换远端、清空基线、头部被旧导出保留但内容已缺字段、父链清理/权限错误；协议异常的只读预检不得改正文或远端。
- 本机未变但远端已变、忽略项在远端存在/缺席、本机独有冲突草稿、设置/保护元数据同时变化；发布不丢未接受远端，基线不误确认。
- 每次网络写入之前、对象创建成功但响应丢失、PATCH 发出前后、CONFIRMING 中及完成标记清除前后中断；跨库日志失败、Compare 无权限/超时/方向反转、成功后被后续提交推进。
- 非空仓库正常发布、空仓库 bootstrap、资产发布集合、不可达对象与用户可见文件的区别。未发布不是对象从未写入，不用“零远端副作用”作为无法实现的验收条件。

D2 已有精确失败消息和两次请求字节数，也已有关闭代理后成功的用户验证；具体代理机制仍可待查，不以查明精确代理限额为条件阻塞 I0 工具落地。步骤 5 在原稿同时被列为“可提前到步骤 4 前”和“依赖步骤 4”，存在矛盾：资源测量与无损投影原型可提前，正式资产发布仍依赖能力门禁及可靠发布；若压力足以影响使用，可另行设计临时传输方案，不绕过这些门禁。

D1/D4 的收敛不取消删除的完整性与授权前提，也不使历史压缩天然安全；仍按第 6 节独立处理。路径分片不按 800 篇自动触发，783 篇也不是迁移条件。第一批保持 I0，只实现统计与只读工具；本次只修订设计，不安装 Flutter、不改数据库或远端格式、不开启自动同步。
