## 3. 兼容门禁与上线顺序

分清三个独立版本：现有导入/导出 `version`（当前接受 1/2）、未来同步封装 `format`、确定性编码 `codec`。应用版本和数据库 schema 版本均不能代替它们。

未来封装的概念字段如下，数值仅为示意，不是已发布格式：

```json
{
  "header": {
    "kind": "nine-rings.sync-snapshot",
    "format": 1,
    "codec": 1,
    "requires": {
      "read": 1,
      "write": 1,
      "readFeatures": [],
      "writeFeatures": []
    },
    "id": "<UTC时间>-<设备短码>-<随机后缀>",
    "parent": { "id": "<上一发布身份>", "sha256": "<上一快照摘要>" },
    "createdAt": "<UTC时间>",
    "writtenBy": { "app": "<版本>", "platform": "<平台>", "deviceId": "<随机设备身份>" }
  }
}
```

读写等级及必需特性集合均须满足；未知的必需特性不能仅凭等级较高就忽略。可另有展示用途的 features 标签，但不得混同安全门禁。继承远端的最低读写等级与特性要求，不因某端未识别字段、当前文档未使用某功能而自动降级；降级只能是明确的格式转换。

“能渲染”“能原样存储/再导出”“能编辑后保留未知数据”“能三方合并”分别验收。Web/Tauri 共享 TS 不代表 Rust 存储往返无损；Flutter 仍需覆盖扩展 Delta、路径/类型/概念、保护数据、模板、未知字段和导出白名单。受限客户端拒写；是否允许只读导入也须满足读取能力。Flutter 插件架构及本地工具安装不在本轮范围。

上线分两步：先交付读取/拒写与共享向量，再在已验证设备上显式开启新写入。**旧二进制不会自行学会检查 header**：无法核实全部写入方已升级时，新格式采用隔离的仓库或命名空间，明确旧空间停止写入，必要时调整旧设备凭据的写权限；不直接覆盖旧 latest。单纯新增 minWrite、修改应用版本或顶层 version 都不能保证阻止所有旧 Push。当前 SyncConfig 尚无分支字段；以分支隔离需先给全部请求绑定显式 ref，不能只改仓库默认分支。

## 4. 已接受实体基线与事务

未来逻辑记录（不是本批数据库迁移）：

| 记录 | 关键字段 |
| --- | --- |
| space | GitHub 主机、owner/repo、显式分支、根路径、format/codec；空间身份变化不复用旧基线 |
| entity baseline | space、entityType、entityId、baseHash、baseMeta、acceptedSnapshot、接收状态；必要时保留基线正文对象定位 |
| sync state | 最近观察到的远端发布、全部确认范围、设备身份、协议/维护代次；不以 seen 等同 accepted |
| attempt | 随机操作 ID、冻结快照身份/摘要、父指针和旧 SHA、预期提交、阶段、确认结果、候选孤立对象 |

这些记录不进入可还原的用户设置，不包含 Token、解锁密钥或明文保护内容。文档、模板、可同步设置、保护元数据及保护历史均要声明实体身份；不能只给 notes 建基线而整份覆盖其他内容。

正文整体冲突判定可以仅保存基线正文哈希，元数据字段合并另存 baseMeta；这能避免常规比较下载完整旧快照。若要提供基于原文的 diff3/冲突展示，则需可获取的基线正文，不能从哈希恢复。正文/源码/书签/引用位置为关联组，路径/保护/密钥标识为关联组；未知元数据也要有保留和比较策略。

Pull 只确认实际接受的实体，忽略、跳过或待解决项保留原基线。文档与基线在同一 IDB/SQLite 事务内更新；涉及模板或 localStorage 时使用可恢复计划与幂等确认，不能声称一个事务覆盖全部存储。上传基线对应**冻结时的内容与修订**；网络期间的新编辑继续为待同步，不能随着成功通知一起清零。

首次升级可下载已接受版本一次建立基线；版本已丢失、空间不符或来源不明时，降级为保守合并，不初始化删除资格。远端成功、本机基线确认失败时记录“远端已发布、本机待确认”，启动后只读核实，不误称上传失败后再写一次。

## 5. 发布协议与不确定结果

保留用户触发的预检和明确 Pull。发现新远端版本，默认阻止当前 Push 并引导安全合并；可在未来提供显式的“合并后重试”，不默认导入远端数据。候选上限三轮只表示有界**重新比较与生成计划**，不代表对 POST/PATCH/PUT 自动原样重放；403/429、校验错误和网络超时也不能一概视作竞争。

推荐顺序：

1. 保存并冻结本地快照、修订与目标空间；读取固定远端 HEAD、指针和能力头。
2. 校验能力及差异计划。无本地逻辑变化且远端已被接受时跳过发布；导出时间、设备显示名、派生搜索字段不制造变化。远端有更新不能误报“已同步”。
3. 准备不可变资产及快照，记录本机 attempt；身份包含随机后缀并绑定字节摘要，不仅靠毫秒时间避免冲突。
4. 优先试验**一个 tree/commit 同时添加快照并更新原路径文本 latest**。保留原 tree 与父提交，非强制推进分支。这样旧读取方仍按原路径取 JSON，同时消除新发布器“两提交之间”的可见窗口；空仓库初始化单独验收。
5. 确认发布结果后确认本机基线；记录与清理分离。

当前 `c2f790a` 仍是快照提交后单独 Contents PUT latest，尚未实现第 4 步。混用旧发布器时，即使新发布器采用同提交，旧代码仍可能独立创建孤立文件；不能宣称整个仓库已获得统一的原子发布协议。`force:false` 约束快进，不是任意条件下严格 expected-HEAD CAS；Contents 旧 SHA 也只约束那个文件，不是整个仓库事务。[Git 引用接口](https://docs.github.com/en/rest/git/refs#update-a-reference)

| 结果 | 处理 |
| --- | --- |
| 明确 HTTP 拒绝 | 停止，保留具体阶段；只有确认属于并发且用户允许时才重新比较 |
| 快照/Blob 成功，指针未发布 | 不记录成功；对象可供后续验证复用，不能仅按文件存在发布 |
| 发布响应丢失或取消 | 只读取得当前指针及提交/摘要，确认本次是否已发布，禁止盲重放 |
| 指针已被后续设备推进 | 检查已记录提交与父链是否证明本次曾成功，不把“现在不指向我”直接当成未成功 |
| 状态无法证实 | 保留待检查，允许导出检查，不自动回滚远端或覆盖本机 |

新 JSON 指针若包含 id/parent/sha256/size，应作为另一次协议升级；不能让现有仅执行 `trim()` 的读取器把整段 JSON 当版本号。完整性摘要不等于签名，也不证明仓库写入方可信。

## 6. 删除、资产和历史回收

删除推断同时要求：同一空间和协议、完整快照声明及全部实体可读、已接受基线、无被忽略/未解决项、已声明该实体种类和覆盖范围、不存在旧客户端漏导。回收站不入当前备份只是现状，不能单凭远端缺少 ID 就授权删除。完整性/能力不满足、远端空白/损坏、新设备或基线重置时只保守合并。

基线推断可以用于完整快照内的已知删除，不强制给所有情形都加墓碑；但离线设备、跨保留窗口、部分同步或按实体增量布局仍需删除代次/墓碑及期限协议。初版仅预览并显式确认，全部远端删除只软删除；受保护/只读文档先冲突，解锁并授权后处理。修改对删除保留两种意图，不自动复活原 ID。`max(5, ceil(0.1 × N))` 可作为额外的批量提醒线，N 为应用计划前本机有效文档数；超过才触发额外确认，不替代任意一条删除的完整性与授权检查。

图片仅在同步投影层外置，本地模型维持原样。64 KiB 只是候选阈值，先量实际完整导出。限定已知图片槽位，不能递归替换任意正文字符串；以类型化引用和能力头避免与用户内容碰撞。校验原始 URI 的 MIME、参数、base64 字母表/填充及字节预算；重编码无法逐字节还原时保留内联，必要时保存原始前缀/表达。规范化 URI 不能悄悄改变正文或其哈希。

资产按内容摘要寻址，下载后核对摘要、长度与 MIME，限制单对象/累计体积。全体必需资产准备并校验后才应用文档；缺失不写成空图或“无该文档”。模板同样受约束。不得从密文提取明文图片；新保护资源协议未就绪时维持完整密文同步，保护范围不同的资产也不能仅因明文字节相同就跨域复用。普通文件夹图片分栏与 PDF/EPUB 原件不因该协议自动进入备份。

保留资源按**所有保留快照、基线、手工检查点及待确认发布**的引用闭包决定；parent 链不可达或超过 24 小时只形成候选，不是删除授权。本机 pending_orphans 不证明其他设备未引用该对象。删除远端文件不等于回收 Git 历史；保留的分支/标签仍可使对象可达，服务端回收时间也不由应用控制。

无父提交加强制更新引用属于独立维护操作，不进入普通 Push、启动修复或自动定时任务。必须单独明确授权、导出回退、核实所有写入方暂停、固定旧 HEAD/保留集合/资产闭包并验证新树。老客户端不认识维护锁或代次时，不能靠一个 JSON 标记保证互斥；不能承诺“只使用路径所以重写历史一定安全”。

## 7. 测量脚本评估与后续工具契约

附件脚本只读 GET，未读取正文，但会输出 owner/repo、分支、文件路径及最大文件清单，并非“只输出统计数字”。本次仅静态审查，没有用其读取真实备份仓库、取得运行中应用令牌，也没有将原脚本直接放入 scripts。

| 脚本现状 | 纳入仓库前需调整 |
| --- | --- |
| 仓库 size / 提交数推算每提交打包体积及年增长 | 删除该因果推断。size 是延迟汇总，不保证是仅此分支的精确 pack 大小；Git 压缩、其他引用与非备份提交会干扰。至少记录同口径多时点差值，分开报告当前未压缩文件量、服务端 size 与成功发布次数 |
| 按一次 Push 两次 commit 换算 | 不固定；空仓库、大快照与未来同提交协议都可能不同，提交总数也不等于成功发布次数 |
| 提交分页只显示不完整提示 | JSON 同时声明覆盖窗口与 lowerBound；未覆盖完整近 90 天时不得输出精确的 90 天节奏。采样起点不能叫仓库首次提交 |
| 递归树截断后仍汇总/投影 | 完整遍历非递归子树或明确返回不完整且停用相关判断；截断不是缺少/已删除 |
| 时间与参数 | 校验仓库/分支、页数上限、正则及日期，过滤未来时间；明确空仓库与无权限，加入请求超时和预算 |
| `GITHUB_API_URL` 任意覆盖 | 发布工具固定 api.github.com；模拟服务器仅显式测试模式且禁止带真实令牌，禁止跨源重定向携带凭据；Token 仅取显式环境变量，不从桌面配置/日志自动提取 |
| 默认展示最大文件路径 | 默认脱敏聚合，详细路径需显式选项；报告不含正文、认证头和完整错误响应 |

下一批 I0 工具应提供离线 fixture 模式和真实只读模式，先验证空仓库、多页、截断、限流、过时/未来时间及参数错误，再对明确目标仓库取样。当前未测真实仓库体积，不能用源码仓库替代。经验性的 500 MiB/三年阈值只是产品候选，不能据此直接重写历史。

运行时导出统计另分正文、记录元数据、search_text、内嵌资源、模板、保护历史、设置及最终 UTF-8/Base64 请求字节；只汇总数量/大小。既有 203 篇统计保留为日期样本，新 783 篇日志只证明完整导出及失败请求大小，无法补出图片分布、仓库增长或未来降幅。

## 9. 分批落地与退出条件

| 批次 | 范围 | 验收 |
| --- | --- | --- |
| I0 | 导出构成与仓库只读测量，修正附件脚本 | 不读正文统计；报告完整性/采样范围；不泄露凭据，不按单点均摊承诺增长 |
| I1 | 能力/封装/编码向量与旧客户端拒写方案 | 同内容跨端哈希一致；未知字段与密文保留；不支持者拒写；先读后写门禁明确 |
| I3 前置 | 逐实体接受状态与 attempt 恢复记录 | 忽略项不误确认；上传中的新编辑保留；本机确认失败能只读恢复 |
| I2/I4 补强 | 同提交快照加文本指针试验，结果不明核实 | 并发不覆盖；单次发布可见性与混用边界有证据；超时不重放；原格式继续可读 |
| I5a | 删除只读计划与显式确认 | 完整性失败零删除，首次还原不推断，修改/回收站/保护冲突不丢失 |
| I5b | 同步投影资产外置 | 标准/非标准 URI、模板、缺失资源、大小预算与保护边界往返通过；所有读取方先支持 |
| 独立维护 | 保留与历史压缩 | 有测量需要且取得单独授权后才交付写操作 |
| 阶段 B 决策 | 按实体文件增量传输 | 依据传输耗时、内存、增长或并发需求，不按文档数自动触发；保留兼容与回退 |
