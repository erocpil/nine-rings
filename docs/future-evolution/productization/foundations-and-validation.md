# 产品基础与验证门槛

> 所属：[Nine Rings 产品化与未来演进](../nine-rings-productization.md)
> 上位方法：[认知与行动方法论](../cognitive-action-methodology.md)
> 相邻：[能力方向](capability-directions.md) · [路线与取舍](roadmap-and-tradeoffs.md)

本文保存当前实现基线、长期产品判断、AI / Agent 职责、产品 Non-goals，以及方法论进入产品化后的三个验证门槛。

## 文档职责

本文只讨论 Nine Rings 如何帮助用户实践认知与行动方法论，以及现有 PKM、跨端、本地数据、AI 和产品路线应如何演进。方法的核心概念、适用边界和有效性假设以方法论文档为单一事实来源；本文不以“功能已经实现”反向证明方法有效。

产品层需要依次验证三个门槛：

1. **表达充分性**：数据模型和交互能否忠实表达方法。
2. **可用性与采纳**：用户是否理解并持续实践，而不产生过重负担。
3. **结果增量**：相较普通文档、静态模板、Agent 或现有 PKM，Nine Rings 是否带来额外净收益。

## 当前实现基线（2026-07-30）

根据当前 React、Tauri、Flutter、存储适配器和自动化测试代码进行静态核对，Nine Rings 已经形成了较完整的 **local-first PKM 基础层**，但尚未实现本文设想的“认知变化发现、检验与复用”闭环。

状态定义：

- **已实现**：已有可使用的数据模型、存储接口和产品入口。
- **部分实现**：已有相关基础能力，但尚未形成本文定义的完整工作流。
- **尚未实现**：当前代码中没有对应领域模型或产品流程。

| 演进方向 | 状态 | 当前实现与边界 |
|---|---|---|

当前已经具备的主要产品能力包括：

- 本地笔记 CRUD、富文本编辑、自动保存、全文搜索、标签管理、置顶和只读。
- 笔记版本快照、恢复前 checkpoint、回收站和删除撤销。
- 按日期组织的随笔、DailyPage 和日常待办。
- 待办子任务、提醒、逾期聚合、跨日继承、拖拽排序和导出。
- Tauri Quick Capture 快捷窗口。
- 文档树、文档/目录移动、P.A.R.A. 路径、Diátaxis 类型和概念标签。
- 手工文档关联、反向链接和目录级 MOC。
- 八个内置模板及模板存储、应用和管理基础。
- JSON 全量导入导出、Markdown 批量导入和单篇 Markdown 导出。
- GitHub 版本化全量备份。
- Web/PWA、Tauri 桌面端和 Flutter 基础移动端。
- Schema、IPC、数据库迁移、导入导出、时区、编辑保存和部分文档树行为的自动化测试。

需要特别避免两种错误映射：

1. 当前 `NoteVersion` 保存的是笔记内容的技术快照，不等于认知意义上的 Revision。Revision 必须表达用户确认的认知变化，并保留变化前后状态、依据和适用语境。
2. 当前概念标签、文档关联、反向链接和目录 MOC 是知识组织结构，不等于 World Model。World Model 应由当前有效 Claim、Revision、Evidence、冲突和不确定性生成，并能够追溯到来源和历史状态。

因此，当前产品已经能够支持“记录、存储、整理、检索、关联和基础行动管理”，但尚不能系统性地支持：

```text
识别事项模式与所需记录强度
  ├─ 普通记录 / 开放探索 / 例行维护
  │    → 保持轻量，不强制进入闭环
  └─ 重要的目标导向事项
       ↓
定义 Goal、Non-goals、Constraints 与 Success Criteria
  ↓
利用知识和当前认知作出 Decision
  ↓
执行 Action 并记录 Cost
  ↓
观察 Outcome 与 Reality，并评估 Benefit
  ↓
接收并保留原始 Feedback
  ↓
完成 Review 与 Evidence Assessment
  ↓
由用户确认 Revision
  ↓
更新可追溯的 World Model
  ↓
影响并检验下一次 Decision
```

这也意味着近期工作的合理顺序仍然是：先完成可信 Beta 和连续的 Daily → Knowledge 基础工作流，再对少量重要事项验证 Decision → Outcome → Review；只有用户持续完成且收益高于记录负担时，才应扩大领域对象和 World Model 投影。

## 1. 核心判断

结合 Nine Rings 已有的“每日一页 + 文档树 + 待办 + 本地优先 + 多端”基础，当前值得小范围验证、但尚未被用户行为和结果数据证实的长期定位是：

> Nine Rings 帮助用户围绕有价值的目标保存判断依据，发现并检验认知变化，跟踪决策、行动与结果，并把现实反馈转化为下一次更好的做法。

这里的“个人认知模型”不是完整、客观、唯一的世界模型，而是一个覆盖用户实际思考与行动领域的 **个人可操作世界模型**。它允许未知、冲突、条件差异和不确定性存在。

知识管理、认知升级和 World Model 都不是最终目的。它们的潜在工具价值，在于帮助用户在一部分真实情境中提高达成目标的概率，并以相称的时间、资源、风险和机会成本减少未经反思的重复错误。它们不适用于所有活动，也不能保证产生更好的 Outcome。World Model 是支持判断和行动的中间基础设施，而不是 Nine Rings 最终交付给用户的产品结果。

对于重要、可行动、存在不确定性且能够获得反馈的目标导向事项，Nine Rings 的完整闭环是：

```text
Goal / Desired Outcome / Success Criteria
  ↓
日常记录 / Source / Claim / World Model
  ↓
Decision / Prediction
  ↓
Action / Cost
  ↓
Reality / Outcome
  ↓
Feedback / Review / Evidence Assessment
  ↓
Benefit 判断与 Revision
  ↓
影响下一次 Decision 与 Action
```

职责边界：

- 用户负责定义什么值得追求、确认成功标准和可接受成本，记录或确认关键决策、现实结果、收益判断与认知变化。
- 系统负责提取候选 Claim、发现变化与冲突、维护来源和历史、保存事前标准、安排验证与回顾，并生成当前认知模型视图。
- 系统不能根据一段随手记录擅自宣布“用户现在相信什么”，也不能把相关性自动解释成因果关系。
- 系统不能仅根据最终 Outcome 判断当时 Decision 的质量，也不能承诺用户一定获得 Benefit。
- Graph、关联、冲突和 World Model 应主要是底层派生结构，而不是要求用户持续手工维护的对象。
- 系统必须允许普通记录、开放探索、关系互动、休息和审美体验停留在非目标化状态，不应强迫所有内容进入实践闭环。

“以时间为入口、以知识网络为沉淀、以本地数据主权为核心的个人工作与知识系统”仍然是近期产品形态，但它是实现上述长期定位的基础设施，而不是最终差异化本身。

### 1.1 定位所依赖的假设

该定位目前是一组需要通过长期使用验证的产品假设，而不是已经成立的事实：

1. 人的部分认知能够表达为带有语境的 Claim、置信度和 Revision，而不只是无法结构化的感受。
2. 用户会持续留下足够的记录，使系统有机会发现重要的认知变化。
3. 用户认为“自己为什么改变看法”具有长期价值，并愿意确认少量关键 Revision。
4. 自动提取 Claim、变化和冲突能够达到可接受的误报率，不会持续扭曲用户原意。
5. 一部分认知变化可以通过 Prediction、Decision、Action 和 Reality 得到现实检验。
6. 长期积累的认知历史能够改善后续判断与行动，而不是退化为另一批无人回顾的档案。
7. 来源、历史、不确定性和系统推导过程足够透明，使用户愿意信任但不会盲从模型。
8. 用户能够为一部分重要事项表达 Goal、Desired Outcome、Success Criteria 和可接受 Cost，并愿意在 Outcome 出现后完成 Benefit 判断。
9. 对依据、决策、执行、外部条件和结果进行复盘，能够提高下一次相似行动的质量或降低成本与风险。
10. 系统能够以足够低的摩擦识别哪些事项值得进入完整闭环，而不会诱导用户把所有生活活动都项目化和量化。
11. 使用 Nine Rings 所增加的记录、分类、确认和回顾成本，长期低于它帮助用户避免的损失或创造的价值。

其中最需要优先验证的是：

- 用户是否愿意持续确认 Revision。
- 自动发现认知变化是否可靠且足够低摩擦。
- 回顾历史 Revision 是否真的改善了后续决策。
- 用户是否愿意在现实结果出现后回来补全验证闭环。
- 用户能否在事前定义足够明确、事后不会随意漂移的 Success Criteria。
- 该闭环是否实际改善 Outcome、使 Cost 与收益更相称，或者产生可复用的能力收益。
- 用户能否自然地区分目标导向事项、开放探索和非工具性活动。
- Nine Rings 增加的记录与回顾负担是否小于用户感知到的收益。

以下情况如果长期出现，应降低、收缩或否定该定位，而不是继续增加领域对象：

- 用户主要使用捕获、编辑和检索，极少愿意关联 Decision、Outcome 或完成 Review。
- 即使交互足够简化，完整闭环的持续完成率仍然很低。
- 结构化字段使用户减少记录、推迟行动或产生明显的自我量化压力。
- 历史 Review 很少被后续 Decision 引用，也没有观察到判断、执行或结果质量改善。
- AI 提出的 Goal、Claim 或因果解释持续制造误导和虚假确定性。
- 用户真正需要的是成熟任务管理、项目协作或专业分析工具，而不是 Nine Rings 的追溯层。

### 1.2 选择该定位的决策依据

当前选择这个方向，主要基于以下判断：

- **差异化**：一般 PKM 优化记录、整理和检索；Goal → Decision → Outcome → Review → Revision 进一步回答“这些知识和认知变化是否帮助用户把重要事情做得更好”。
- **现有能力匹配**：每日记录、文档、待办、版本历史、本地存储和回顾入口，可以逐步演化为认知变化系统，不需要立即重写为知识图谱产品。
- **维护成本**：要求用户手工维护完整 Graph 通常不可持续；从自然记录中派生结构，再由用户确认少量关键变化，更符合低摩擦原则。
- **可形成闭环**：Revision 可以影响 Decision，Decision 可以产生 Prediction 和 Action，Reality 又能反过来触发下一次 Revision。
- **价值可验证**：Goal、Success Criteria、Cost、Outcome 和 Benefit 使产品价值不再停留于“保存了多少知识”，而可以检查是否改善了行动结果、学习速度或风险控制。
- **本地数据价值**：认知历史高度私人且具有长期性，本地优先和可导出能力是这个定位的必要条件，而不只是技术偏好。

这些依据主要来自产品逻辑、现有架构和差异化推演，不等同于市场验证、因果证据或付费意愿。它们最多支持低成本原型和行为实验，不能证明“认知闭环”一定比更简单的 Daily、搜索、任务或回顾功能创造更多用户价值。

这些依据目前只足以支持小范围验证，尚不足以把全部开发资源投入完整 World Model。第一阶段必须先证明以下最小链路能够稳定发生：

```text
用户或系统识别出值得管理的目标导向事项
  ↓
用户定义 Goal / Non-goals / Constraints / Success Criteria
  ↓
系统提出候选 Claim 或 Revision
  ↓
用户确认或修正
  ↓
关联一次 Decision / Prediction / Action / Cost
  ↓
Outcome 与 Feedback 出现
  ↓
用户完成 Review，并判断 Benefit 与下一步调整
```

如果这条链路不能持续发生，World Model 就没有可靠的数据基础，也没有证据证明认知升级能够转化为真实收益。

因此，更完整的产品命题是：

> Nine Rings 帮助用户围绕重要目标保存依据、作出可检验的决策、跟踪行动与结果，并把现实反馈转化为下一次更好的做法。

Nine Rings 不必成为通用项目管理或执行引擎。它应重点维护 Goal、依据、Decision、Action、Outcome、Feedback、Revision 和 Benefit 之间的可追溯关系；具体执行可以继续由专业工具、人、AI、Agent 或 Skills 完成。

## 2. AI、Agent、Skills 与 Nine Rings 的职责

AI / Agent / Skills 适合：

- 建议当前内容更接近目标导向、开放探索、例行维护还是普通记录，并允许用户忽略建议。
- 从自然语言中提出候选 Goal、Desired Outcome、Success Criteria 和 Cost。
- 从记录和外部事件中发现候选 Feedback。
- 建议关联的 Claim、Decision、Prediction 或 Action。
- 比较 Outcome 与事前 Success Criteria，提示成本超支和标准漂移。
- 聚合重复信号并提示可能冲突。
- 生成 Review 草稿和替代解释。
- 提醒缺少 Feedback 的重要 Decision。
- 根据历史提出候选 Revision。
- 主动建议某些低价值事项不要进入完整闭环，减少不必要的结构化。

Nine Rings 原生核心负责：

- 持久保存原始 Feedback 和来源。
- 维护 Goal、Decision、Action、Outcome 等对象的身份、时间、状态和关联。
- 保存用户选择的事项模式、Non-goals 和 Constraints，但不把模式推断自动升级为事实。
- 保存 Success Criteria、预期 Cost 和 Prediction 的事前版本，避免被结果覆盖。
- 保存用户确认及撤销历史。
- 调度到期 Review。
- 防止自动推导覆盖原始事件。
- 在更换 Agent、Skill 或模型后仍保持数据语义稳定。

原则仍然是：

> AI 负责发现、提议和解释；Nine Rings 负责持久化、调度、追溯与确认。

### 2.1 分阶段实现

早期不必立即建立独立 Feedback 数据表。

**阶段 A：Typed Observation**

- 将 Feedback 作为带类型的 Observation 保存。
- 记录来源、原始内容、时间和候选目标。
- 先允许用户选择普通记录、开放探索或目标导向事项。
- 对目标导向事项，通过轻量元数据表达 Goal、Non-goals、Constraints、Desired Outcome、Success Criteria、Decision、Cost 和 Outcome，不增加复杂用户界面。

**阶段 B：Review Queue**

- 增加“待处理 Feedback”视图。
- 支持关联 Claim / Decision / Prediction。
- 保存 Review 结果、替代解释和用户确认。
- 用 Skills 验证用户是否愿意完成处理闭环。

**阶段 C：First-class Feedback**

只有在以下需求反复出现后，才升级为独立领域对象：

- 一条 Feedback 需要关联多个目标。
- 同一 Feedback 需要多次或多人 Review。
- 需要独立的状态、提醒和权限。
- 需要区分原始信号与多个 Evidence Assessment。
- 用户持续使用 Feedback 队列并由此产生 Revision。

**阶段 D：认知可观测性**

- 展示端到端 Trace：Goal → Claim → Decision → Action → Outcome → Feedback → Revision → 下一次行动。
- 显示未验证 Claim、缺失 Feedback、长期未 Review 的 Decision 和重复失败模式。
- 显示未定义 Success Criteria、Cost 超出预期、Outcome 已出现但 Benefit 尚未判断的事项。
- 生成 World Model 当前投影，但允许回到任意历史时点检查当时依据。

### 2.2 最小验证指标

Feedback 能力是否值得产品化，应至少观察：

- 候选 Feedback 被用户确认相关的比例。
- Feedback 进入 Review 的比例。
- Review 最终产生 Revision、保持原判断或标记无法判断的分布。
- 重要 Decision 在到期后获得 Feedback 的比例。
- 用户是否会再次查看历史 Feedback 和当时依据。
- Agent 建议的错误关联率和撤销率。
- Feedback 闭环是否影响下一次 Decision，而不只是生成更多记录。
- 有明确 Success Criteria 的重要 Goal 比例。
- Outcome 出现后完成 Cost 与 Benefit 判断的比例。
- 相似事项中，目标达成率、决策校准度、完成周期、返工、Cost 或风险是否改善。
- 历史 Review 是否被下一次 Decision 实际引用和复用。
- 用户完成结构化记录和 Review 所增加的时间、认知负担与放弃率。
- 用户选择普通记录、轻量闭环和完整闭环的分布，以及系统推荐错误升级的比例。

真正重要的指标不是保存了多少 Feedback，而是：

> Feedback 是否让用户更准确地解释过去，在下一次相似情境中作出不同且可检验的判断，并以与价值相称的 Cost 和风险获得更有价值的 Outcome。

目标达成率本身不能作为唯一指标：它可能因为用户只选择更简单的 Goal、事后降低 Success Criteria、放弃困难事项或忽略外部 Cost 而上升。评估时应同时检查目标难度、选择偏差、标准变更、未完成样本和 Nine Rings 本身造成的摩擦。

## 3. 产品 Non-goals

为了避免“个人实践系统”扩张为无边界的生活管理平台，至少应明确以下产品 Non-goals：

- 不替用户定义什么人生目标、价值观或 Benefit 才是正确的。
- 不要求所有笔记、阅读、关系和休闲活动绑定 Goal 或产生可量化 Outcome。
- 不以最大化任务完成数、工作时间或表面生产率作为默认目标。
- 不保证更完整的记录一定产生更好 Decision，也不保证好 Decision 一定产生好 Outcome。
- 不用单一分数评价用户的认知质量、人生进展或知识健康度。
- 不把所有 Cost、风险和伦理边界折算成一个可以被 Benefit 抵消的数值。
- 不替代专业项目管理、财务、医疗、法律、科研统计和团队协作工具。
- 不允许 AI 自动确认用户的 Goal、信念、因果归因、Benefit 或 Revision。
- 不通过制造数据锁定、连续打卡压力或未完成羞耻维持用户活跃。

这些 Non-goals 不是永久禁止任何相关能力，而是对产品默认行为和近期范围的约束。如果未来改变，必须有明确用户证据、风险评估和可退出设计。

## 4. 方法论与 Nine Rings 产品化必须分离

目前的讨论实际上包含两个不同问题：

1. **方法论问题**：人是否应该在适当情境中区分事项模式、Goal、Non-goals、Constraints、Unknowns、Trade-offs、Outcome、Feedback 和 Revision。
2. **产品问题**：Nine Rings 应怎样以低摩擦、可追溯、可退出的方式帮助用户实践这套方法。

方法论不依赖 Nine Rings。用户可以使用纸张、普通 Markdown、电子表格、设计文档或一次 Agent 会话实践它。Nine Rings 只有证明自己比这些替代方式更可靠、更连续或更低摩擦，才具有产品层面的增量价值。

更严格地说，需要分别验证四层假设：

| 层次 | 核心问题 | 不能用什么替代证据 |
|---|---|---|
| 方法有效性 | 这套区分是否改善问题理解、Decision、学习或 Review | 不能用“概念听起来完整”证明 |
| 表达充分性 | Nine Rings 的数据模型能否忠实表达方法且不扭曲语义 | 不能用“字段已经实现”证明 |
| 可用性与采纳 | 用户是否理解、愿意填写，并能在真实工作流中持续完成 | 不能用单次演示或开发者自用证明 |
| 结果增量 | 使用 Nine Rings 是否比普通文档、模板、Agent 或其他工具带来更好的净结果 | 不能用活跃度、记录数或主观喜欢证明 |

这四层可以归入两个相对独立的讨论对象：

| 讨论对象 | 对应假设 | 首要问题 |
|---|---|---|
| 认知与行动方法论 | 方法有效性 | 不依赖 Nine Rings，这套方法是否值得实践 |
| 通过 Nine Rings 实践方法论 | 表达充分性、可用性与采纳、结果增量 | Nine Rings 是否能忠实、可持续且更有净收益地帮助用户实践 |

因此，二者存在明确的逻辑依赖：如果方法本身缺乏适用边界、可执行性和可证伪性，就不应直接把它固化为 Nine Rings 的核心数据模型和交互流程。否则，产品可能只是把尚未成立的方法做得更复杂、更难退出。

但这种顺序不应被理解为严格瀑布式过程，即“先在产品之外彻底证明方法，再开始任何产品设计”。方法论的实际效果具有情境依赖性，而且表达成本、提醒时机和反馈周期本身也会影响方法能否被执行。更合理的顺序是：

1. 先形成一个最低可验证的方法论版本：概念清晰、适用边界明确、可由纸张或普通文档执行、提出可观察结果和证伪条件。
2. 先用普通文档、静态模板或 Agent 会话做低成本实践，检验用户是否理解、是否愿意使用，以及哪些步骤真正产生价值。
3. 只把反复出现、跨时间难以维持、依靠普通工具成本较高的问题交给 Nine Rings 产品化。
4. 再用产品实践结果反向修正方法论，但必须区分“方法无效”和“产品实现失败”。

这里的“先确认方法论”应指达到**值得进入实践验证的最低可信度**，而不是宣称方法已经普遍有效。最低可信度至少包括：

- 问题、目标用户和适用情境可以被描述。
- 核心概念之间没有明显矛盾或循环定义。
- 方法可以在不依赖 Nine Rings 的情况下手工执行。
- 预期收益、成本、副作用和替代方案已经显性化。
- 存在能够使方法被削弱、修改或放弃的观察结果。

这四层可能出现不同结果：

- 方法本身合理，但 Nine Rings 交互过重，产品失败。
- Nine Rings 很好用，但用户只把它当普通 PKM，方法没有被实践。
- 用户持续完成闭环，但没有观察到 Decision 或 Outcome 改善。
- 结果有所改善，但主要来自 Agent、模板或用户投入了更多时间，而不是 Nine Rings 的特定能力。

因此，功能设计应从方法需求推导，但不能把两者等同：

| 方法论需求 | Nine Rings 可以提供的产品支持 |
|---|---|
| 判断事项模式 | 可忽略的模式建议，不在捕获时强制分类 |
| 澄清 Goal、Non-goals 和 Constraints | 渐进式模板、轻量元数据和版本历史 |
| 保存 Unknowns 与 Exploration Question | 问题视图、来源关联和后续提醒 |
| 记录 Prediction 与 Success Criteria | 事前快照、变更原因和不可静默覆盖的历史 |
| 连接 Decision 与 Action | 关联任务、触发条件、调整条件和外部执行工具 |
| 接收 Outcome 与 Feedback | 低摩擦捕获、到期提醒和 Review Queue |
| 形成 Revision | 用户确认、证据引用、前后状态和撤销历史 |
| 允许非目标化活动 | 普通笔记默认路径、无必填字段、随时降级或退出 |

对应的验证也必须分开：

- 方法论实验关注 Decision 质量、Prediction 校准、返工、错误复发和 Review 复用。
- 产品实验关注完成率、理解错误率、记录耗时、放弃率、用户压力和跨端可靠性。
- 增量价值实验需要与普通文档、静态模板、Agent 会话或现有 PKM 做比较。
- 结果评估需要保留未完成和负面样本，不能只观察主动使用完整闭环的高动机用户。

Nine Rings 在这套方法中的合理职责仍然是：持久化、版本化、关联、调度、追溯和确认。AI / Agent / Skills 可以发现、建议、解释和执行；方法论决定“应该思考哪些问题”，产品决定“怎样让这些问题在长期实践中不被遗忘且不过度增加负担”。

### 4.1 文档边界也应随之分离

现在把两类内容拆成至少两个文档是合理的，因为它们面向不同问题、证据和变更节奏：

1. **方法论文档**：独立于 Nine Rings，定义要解决的问题、适用边界、核心概念、流程、理论依据、竞争解释、成本、风险、可证伪假设和低技术验证方法。
2. **Nine Rings 产品化文档**：引用一个明确版本的方法论，讨论数据模型、交互、AI / Agent 分工、渐进披露、迁移与退出、实现阶段和产品验证指标。

如果后续实验增多，可以再建立第三份**验证与研究记录**，保存实验设计、样本、失败案例、结果和方法修订理由，避免把动态证据不断堆入相对稳定的方法定义。

拆分也有风险：术语可能漂移、同一结论可能被重复维护、产品文档可能悄悄改变方法论。为降低这些风险，应让方法论文档成为概念与适用边界的单一事实来源；产品文档只引用它，不重新定义同一术语；方法发生重要变化时记录版本和迁移影响。

因此，建议现在开始分离，并优先讨论方法论，但暂不把当前文档机械切割成互不关联的两半。应先确定方法论文档的最小目录和核心命题，再迁移相关内容；当前文档则逐步收敛为 Nine Rings 的产品演进与验证路线。

不建议直接与 Notion、Obsidian 等产品比拼功能数量。Nine Rings 更有机会形成差异化的组合是：

```text
快速捕获
  ↓
每日处理
  ↓
转化为长期知识
  ↓
建立概念和关联
  ↓
判断事项模式
  ├─ 普通知识 / 开放探索
  │    → 保留来源、问题和关联
  │
  └─ 重要的目标导向事项
       ↓
     Goal / Non-goals / Constraints
       ↓
     Decision / Action / Outcome
       ↓
     Review / Revision / Benefit 判断
       ↓
     复用于下一次相似事项
```

项目下一阶段的重点，应从“继续增加独立功能”转向：

1. 建立连续、低摩擦的核心工作流。
2. 让本地数据和跨端行为足够可信。
3. 强化“时间 × 知识 × 行动结果”的产品差异。
4. 根据真实用户选择重点平台和重点人群。

### 4.2 产品验证命题

从产品验证角度看，“帮助用户提高目标达成概率”只能作为使命，不能直接作为可检验的 Goal，因为它缺少用户群、事项类型、基线、时间范围和归因方式。真正的产品实验必须限定情境，例如观察用户是否会在重复出现的技术决策中引用历史 Review、提高 Prediction 校准度、减少同类返工，并同时测量使用 Nine Rings 增加的时间与认知负担。
