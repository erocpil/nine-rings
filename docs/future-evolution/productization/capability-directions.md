# 产品能力方向

> 所属：[Nine Rings 产品化与未来演进](../nine-rings-productization.md)
> 相邻：[产品基础与验证门槛](foundations-and-validation.md) · [路线与取舍](roadmap-and-tradeoffs.md)

本文讨论知识工作流、同步、隐私、AI、任务、垂直人群、平台、插件、发布和商业化等候选方向。它们是待选择的能力空间，不等于已批准的近期范围。

## 5. 主方向：从便签应用升级为个人知识工作台

这是与当前代码和用户入口衔接最自然的路线，但“开发衔接自然”不等于“市场成功概率最高”。是否值得继续投入，仍取决于用户能否持续完成捕获、整理和回顾，以及这些行为是否产生可感知价值。

### 5.1 Inbox：统一捕获入口

Inbox 用于接收尚未整理的内容：

- Quick Capture 快速记录。
- 系统分享菜单传入的文字、链接和图片。
- 浏览器剪藏。
- 剪贴板历史中的主动摘录。
- Markdown 和其他格式导入。
- 邮件、日历或第三方自动化产生的记录。

捕获阶段应尽量少要求用户填写分类、标签和文档类型。整理工作应发生在后续流程中。

### 5.2 Daily：当天工作中心

每日一页不只是按日期筛选笔记，而应成为当天的工作台：

- 今日笔记与 Quick Capture。
- 今日计划和截止任务。
- 逾期任务与重新计划。
- 当天修改过的项目和文档。
- 最近需要回顾的知识卡片。
- 日程和提醒。
- 当日总结入口。

### 5.3 Distill：从碎片转为长期知识

支持将每日记录逐步提炼：

- 随笔一键转为永久笔记或项目文档。
- 从一篇记录中拆分多个知识卡片。
- 将多个碎片合并为一篇结构化文档。
- 自动保留原始日期和来源链接。
- 建议 P.A.R.A. 目录、Diátaxis 类型和概念标签。
- 标记“已处理”“待整理”“无需沉淀”。

这一步是 Nine Rings 从日记工具走向知识系统的关键。

### 5.4 Review：周期回顾

建立日、周、月三个层级的回顾：

- 日回顾：完成事项、新增知识、未解决问题。
- 周回顾：项目进展、逾期任务、高频概念、待整理记录。
- 月回顾：主要成果、长期趋势、停滞项目和下一周期目标。
- 自动生成回顾草稿，用户确认后写入普通文档。
- 所有自动总结都能追溯到原始笔记和任务。

### 5.5 Archive：完成后的知识保留

- 已完成项目转入归档。
- 项目任务不再进入活动视图。
- 项目产生的知识文档和概念关系继续保留。
- 回顾页面能够引用历史项目成果。

## 6. 差异化方向：强化“时间 × 知识 × 行动结果”

多数笔记产品更偏向其中一端：

- 日记和待办工具强调时间，但知识沉淀较弱。
- 知识库工具强调目录和链接，但每日使用入口较重。

Nine Rings 可以先连接时间与知识，再进一步关联 Goal、Decision、Action 和 Outcome，使用户不仅能找到“过去记录过什么”，还能理解“这些知识后来怎样影响行动、结果和收益”。

### 6.1 时间视图

- 日历热力图展示每天的笔记、任务和项目活动。
- 今日、昨日、本周、本月的统一查询视图。
- “历史上的今天”。
- 某篇文档的创建、引用和修改时间线。
- 某个概念随时间的发展过程。

### 6.2 知识健康度

- 长期未更新但仍处于活动项目中的文档。
- 没有入链或出链的孤立文档。
- 只有临时记录、尚未形成长期文档的主题。
- 重复或高度相似的笔记。
- 有大量引用但缺少 MOC 的概念。
- 已完成项目中值得沉淀、但尚未整理的内容。

### 6.3 间隔回顾

- 根据创建时间、访问频率和重要度安排回顾。
- 用户可标记“已掌握”“需要复习”“不再提示”。
- 回顾时显示相关历史记录、关联概念和最新变化。

“时间 × 知识”比继续增加普通编辑器按钮更有机会形成产品壁垒。

## 7. 同步方向：从备份演进为真正的 local-first

当前 GitHub 功能本质上是版本化全量备份。建议分三个阶段演进。

### 7.1 第一阶段：可靠备份

近期应先把备份能力做扎实：

- 将用户可见名称明确为“GitHub 备份”。
- 支持自动备份和保留策略。
- 为快照增加校验和、大小和数据版本。
- 恢复前展示备份时间、内容摘要和差异。
- 支持恢复单篇笔记或单个日期页面。
- 支持本地加密后再上传。
- 扩展 WebDAV、本地目录和 S3 兼容存储。
- 清理超过保留期限的历史快照。

### 7.2 第二阶段：多设备增量同步

建立统一的实体变更日志：

- 每次修改产生 entity operation。
- 每台设备拥有独立 `device_id`。
- 每个实体拥有单调版本或逻辑时间。
- 笔记、任务、标签、附件分别同步。
- 删除使用 tombstone 传播。
- 同步具有断点续传和幂等性。
- 冲突时保留双方版本，不静默覆盖。
- 提供冲突比较与合并界面。

建议同步模型至少包含：

```text
operation_id
device_id
entity_type
entity_id
action
base_version
new_version
timestamp
payload
```

### 7.3 第三阶段：实时协作

只有在出现明确团队需求后再考虑：

- Yjs、Automerge 或其他 CRDT。
- 实时光标和多人编辑。
- 共享空间、成员和权限。
- 服务端中继。
- 历史审计。
- 评论、审批和通知。

实时协作会显著改变成本、隐私模型和产品定位，不适合作为近期主线。

## 8. 隐私与数据主权方向

Nine Rings 适合发展成隐私优先的个人工具。

### 8.1 基本原则

- 默认数据只保存在本地。
- 不注册账号也能使用全部本地功能。
- 数据目录和格式公开。
- 随时可导出为可读的 Markdown/JSON。
- 不通过封闭格式制造迁移成本。

### 8.2 安全能力

- 应用锁。
- 单篇文档加密。
- 附件加密。
- 端到端加密同步。
- 备份完整性校验。
- 密钥恢复和轮换。
- Tauri/Flutter 使用系统安全存储保存 Token。

### 8.3 可选择的存储方式

- 纯本地。
- GitHub。
- WebDAV。
- S3 兼容服务。
- 用户自托管服务。
- 官方托管同步。

如果能够做到可靠、透明和可迁移，“数据主权”会成为相对云端笔记产品的重要优势。

## 9. AI 方向：作为整理助手，而不是聊天入口

AI 可以成为 Nine Rings 的增强能力，但不应把产品变成普通的 AI 聊天笔记。

最适合的能力是参与“捕获 → 整理 → 关联 → 回顾”的完整流程。

### 9.1 捕获与整理

- 从当天记录中提取待办。
- 将随笔整理成结构化永久笔记。
- 将长记录拆分为多个原子笔记。
- 推荐标题、标签、概念和文档类型。
- 将会议记录提取为决策、行动项和未解决问题。

### 9.2 关联与发现

- 推荐相关文档。
- 推荐潜在双向链接。
- 发现重复、矛盾或可合并的笔记。
- 生成主题 MOC 草稿。
- 发现长期没有得到回答的问题。

### 9.3 回顾与检索

- 生成每日、每周和每月回顾草稿。
- 基于本地知识库回答问题。
- 回答必须展示来源文档和相关原文。
- 对选中内容改写、总结、翻译或解释。

### 9.4 隐私要求

- 支持用户自带 API Key。
- 支持 OpenAI 兼容接口。
- 支持 Ollama 或其他本地模型。
- 明确展示哪些内容将发送给模型。
- 可选择只发送当前选中内容。
- 向量索引和原文默认保存在本地。
- 默认不使用用户内容训练模型。

真正有差异化的不是增加一个聊天框，而是 AI 是否能降低知识整理和回顾的成本。

## 10. 任务与项目管理方向

目前待办嵌入 `DailyPage`，适合简单日常管理，但不适合长期项目。

### 10.1 独立 Task 实体

未来可将任务升级为独立实体：

- 稳定 ID。
- 创建时间、计划日期、截止日期、完成日期分离。
- 项目、上下文、优先级。
- 重复规则。
- 子任务与依赖关系。
- 关联笔记、文档和概念。
- 状态变更历史。

每日页面只负责显示当天任务视图，不再拥有任务本体。

### 10.2 跨日行为

未完成任务不应简单复制到第二天，而应提供：

- 重新计划。
- 保持截止日期但显示逾期。
- 移入以后处理。
- 取消或归档。

这样可以避免同一任务在多个日期页面产生重复副本。

### 10.3 项目聚合

项目页面自动聚合：

- Goal、Desired Outcome 和 Success Criteria。
- 预期与实际 Cost。
- 关联任务。
- 关联笔记和文档。
- Claim、Decision 和 Prediction。
- 里程碑。
- Action、最近活动和 Outcome。
- Feedback、Benefit 判断和 Revision。
- 回顾与归档。

建议保持克制，不必发展成 Jira。Nine Rings 不需要替代专业排期、工单和团队执行工具；它更应维护“目标—依据—决策—行动—结果—复盘—收益”的可追溯关系，目标是“知识工作中的实践改进”。

## 11. 垂直人群方向

### 11.1 开发者与技术研究者

这一方向与现有 Diátaxis、代码块、本地 Markdown 和文档树能力最契合。

可发展：

- Git 仓库关联。
- 代码片段库。
- ADR、RFC、排障记录模板。
- Markdown 文件夹双向同步。
- 命令行快速记录。
- VS Code/JetBrains 插件。
- 文档中引用 commit、issue、文件和代码位置。
- 自动生成项目 MOC。
- 技术文档健康检查。

### 11.2 研究与学习

- 文献和网页剪藏。
- PDF 标注引用。
- 引文与参考文献管理。
- 概念卡片。
- 间隔复习。
- 学习计划与知识掌握度。
- 从课程笔记生成复习问题。

### 11.3 写作者

- 大纲与章节树。
- 卡片式素材管理。
- 引用和人物关系。
- 写作版本比较。
- 写作目标、字数和每日进度。
- Markdown、PDF、EPUB 导出。

不建议同时面向全部人群。根据现有技术和产品基础，优先级建议为：

1. 开发者与技术研究者。
2. 一般知识工作者。
3. 学习者。
4. 专业写作者。

## 12. 平台策略

目前同时维护 React/Tauri/Flutter，长期成本很高。

### 12.1 推荐策略：Web/Tauri 为主，Flutter 做移动伴侣

- Web/Tauri 承担完整编辑、文档管理和设置。
- Flutter 首先做好快速捕获、搜索、阅读、待办和同步。
- 移动端不急于复制所有桌面功能。
- 桌面端负责重度整理，移动端负责随时记录和查看。
- 共享数据契约和兼容测试，不强求 UI parity。

这是当前最能控制维护成本的方式。

### 12.2 可选策略：统一跨端实现

如果团队长期规模有限，可在积累真实平台使用数据后考虑收敛：

- React + Tauri 覆盖桌面，Web 直接发布。
- 移动端使用高质量 PWA、Capacitor 或 Tauri Mobile。
- 或完全转向 Flutter，但会失去现有 Web 编辑器生态和成熟实现。

现在不建议立即重写。应先统计真实用户的平台分布、使用时长和功能差异，再决定是否收敛。

### 12.3 各端建议职责

| 平台 | 建议职责 |
|---|---|
| Web | 无安装体验、跨设备访问、轻量编辑、演示与分享 |
| Tauri | 完整桌面功能、本地文件、快捷键、托盘、重度编辑 |
| Flutter | 快速记录、搜索、阅读、待办、提醒、移动同步 |

## 13. 插件与自动化生态

核心数据模型和同步协议稳定后，可以考虑插件系统。

### 13.1 插件类型

- 模板插件。
- 导入导出插件。
- 自定义侧栏和聚合视图。
- 命令面板命令。
- 自动化规则。
- AI Provider。
- 同步 Provider。
- 主题和编辑器扩展。

### 13.2 自动化示例

- 创建会议记录时自动添加模板和标签。
- 完成项目后自动生成回顾并归档。
- 每周五生成周回顾草稿。
- 保存带特定标签的笔记时同步到外部目录。
- 新建技术文档时自动创建对应 ADR 或 MOC。

### 13.3 安全边界

插件系统应使用受限 API：

- 明确声明权限。
- 默认不能访问全部数据库。
- 默认不能访问任意文件路径。
- 网络请求需要单独权限。
- 敏感 Token 由宿主安全存储。
- 插件错误不能破坏主数据库事务。

## 14. 发布与分享方向

知识沉淀后，用户通常需要选择性输出。

可以发展：

- 单篇文档发布。
- 选定目录发布为静态知识站点。
- MOC 发布为导航页。
- 隐私链接和过期链接。
- Markdown、HTML、PDF、EPUB 导出。
- 文档快照分享，不暴露整个数据库。
- 可选择隐藏内部链接、标签和属性。

发布应是本地内容的受控出口，不应迫使用户将整个工作区迁移到云端。

## 15. 商业化可能

Nine Rings 适合“本地核心免费、增值服务付费”的模式。

### 15.1 可付费能力

- 官方端到端加密同步。
- 托管备份。
- 多设备同步和历史保留。
- AI 用量或本地 AI 增强包。
- 专业导出和发布。
- 团队空间与协作。
- 企业自托管。
- 一次性桌面 Pro 许可证。

### 15.2 不建议限制的能力

- 本地数据访问。
- 基础 Markdown/JSON 导出。
- 用户自己的备份。
- 本地全文搜索。
- 基础编辑和知识链接。

通过限制数据导出制造锁定，会破坏 local-first 产品最重要的信任基础。
