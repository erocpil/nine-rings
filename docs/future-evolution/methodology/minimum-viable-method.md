# 最小可验证方法论

> 所属：[认知与行动方法论](../cognitive-action-methodology.md)
> 相邻：[语义模型与适用边界](semantic-model-and-boundaries.md) · [理论证据与案例](evidence-and-cases.md)
> 状态：v0.1，尚未完成行为与结果验证

本文定义独立于 Nine Rings 的最短认知与行动闭环、验证单位、低成本实验、否定条件和示例。产品实现不属于本文范围。

## 1. 核心命题与研究边界

本文讨论的不是“怎样使用某个 PKM”，而是一个更基础的问题：

> 对重要、可行动、存在不确定性并能够获得反馈的事项，保存事前判断，连接 Decision、Action 与实际 Outcome，区分原始 Feedback 与事后解释，并明确确认 Revision，是否能让认知变化更容易被发现、检验和复用？

预期的最终价值，是提高实践者在相似情境中作出更合适判断与行动的概率，并减少不必要的返工、风险和重复犯错。但这属于远端结果，受能力、执行、环境和运气共同影响，不能作为方法早期唯一的有效性证据。

方法的近期、可检验目标应更克制：

- 能否还原“行动前实际怎么想”，而不是只保留事后叙述。
- 能否发现 Prediction、Outcome 和解释之间的差异。
- 能否区分认知、Decision、执行、环境和测量分别出了什么问题。
- 能否形成具体 Revision，或者有依据地维持原判断。
- 后续相似事项是否实际检索并使用了这次 Review。
- 上述收益是否大于记录、等待和回顾造成的成本。

本文不假设所有生活都应目标化，也不假设更完整的记录必然产生更好结果。开放探索、例行维护、非工具性活动和低风险选择可以使用其他模式，或者完全不记录。

## 2. 最小可验证方法论 v0.1

“最小”不是把完整概念表全部变成必填字段，而是找出足以产生并检验核心价值的最短闭环。第一版只验证目标导向的 Decision Episode；开放探索、长期习惯和纯知识积累暂不进入同一个实验。

### 2.1 验证单位与进入条件

最小验证单位是一次**可复盘决策事项**：

> 某个人在具体语境中，基于当时的认识作出一个会引发行动或明确不行动的 Decision，之后能够观察到与其 Prediction 或 Desired Outcome 有关的 Feedback。

事项至少应满足：

1. **有一定影响**：结果值得事后检查，而非低成本、可逆的琐事。
2. **存在真实不确定性**：不是机械执行已经确定的答案。
3. **能够获得 Feedback**：在可接受时间内有机会观察结果或有效代理信号。
4. **可能复用**：未来存在相似判断，Review 不只是一次性解释过去。

不满足这些条件时，普通笔记、任务清单、检查表或不记录通常更合理。第一轮验证建议优先选择技术排障、产品取舍、学习策略等反馈相对清楚的事项，不直接声称适用于人生选择、关系、伦理或长期社会判断。

### 2.2 最短闭环

```text
判断是否值得复盘
  ↓
冻结事前状态
  ↓
Decision / Action
  ↓
记录 Outcome 与原始 Feedback
  ↓
比较预期与实际，检查替代解释
  ↓
确认 Revision / 暂不 Revision
  ↓
形成下一次可检索的使用条件
```

一次最小记录只要求回答六个问题；它适用于仍有数十秒到数分钟进行思考的可复盘 Decision。若可用时间短于记录时间，应使用核心体系定义的“立即行动”或“极速基线”，先执行预案或写下关键假设与停止 / 升级条件，局面稳定后再决定是否复盘。

**行动前**

1. **事项与意图**：现在需要判断什么，为什么值得处理？
2. **当前判断与可观察预期**：目前相信什么，预计会发生什么？
3. **Decision 与 Review Trigger**：决定做什么或不做什么，何时回来检查？

**结果出现后**

4. **Outcome 与原始 Feedback**：实际发生了什么，付出了什么，收到了哪些尚未解释的信号？是否有反例、缺失信号或被忽略的材料？
5. **Review**：预期与实际哪里一致、哪里不一致？认知、Decision、执行、环境和测量分别可能有什么影响？最强替代解释和会改变结论的证据是什么？
6. **Revision 与 Reuse Rule**：什么认识发生了变化？如果没有变化，理由是什么？下次什么情境应检索这次记录？

Goal、Desired Outcome、Prediction 等概念在这六个问题中可以合并表达，但分析时仍需避免混淆。Non-goals、Constraints、Unknowns、Trade-offs、详细 Success Criteria、Evidence Assessment 和置信度不是每次都必须填写；当它们会改变 Decision 或结果解释时，再升级为扩展记录。**概念需要区分，不等于每个概念都必须成为独立字段。**

低风险事项中的“反例 / 改变结论的证据”可以只写一句、写“尚不清楚”，或在不影响 Decision 时省略；它不把最小闭环变成完整的证据审查。独立质询只适用于高风险、不可逆、涉及他人利益或重复重大失败的事项，不能作为所有个人记录的必填项。

### 2.3 预期作用机制

这套方法成立需要至少四个作用机制：

1. **事前状态可追溯**：在 Outcome 出现前保存判断与标准，减少事后记忆重写和成功标准漂移。
2. **反馈进入闭环**：预先约定 Review Trigger，降低行动完成后不再回看的概率。
3. **解释得到约束**：把原始 Feedback、Evidence Assessment 和 Revision 分开，迫使实践者考虑执行、环境、测量及替代解释。
4. **学习能够迁移**：把 Revision 写成带适用条件的下一次判断规则，而不只形成一篇事后总结。

任何一个机制长期不发生，都可能使方法退化为较复杂的决策日志。

### 2.4 “一个方法假设”实际是一个假设族

在产品决策中，可以把“方法有效性”作为第一道总门槛；但研究上它不是一个不可再分的原子假设，至少包含：

| 子假设 | 需要观察什么 |
|---|---|
| 可理解性 | 实践者能稳定区分 Goal、Prediction、Outcome、Feedback、Review 与 Revision |
| 可执行性 | 不依赖专用软件，也能在真实事项中完成最短闭环 |
| 认知可观测性 | 事前记录与事后结果的差异能暴露原本难以发现的认知变化 |
| 解释质量 | Review 比自由复盘更少出现后见之明、单因归因和标准漂移 |
| 迁移与复用 | Revision 会在后续相似 Decision 中被检索并改变判断或行动 |
| 净收益 | 上述收益大于记录时间、认知负担、自我量化压力和延迟行动的成本 |

这些子假设可以独立失败。例如，方法可能容易理解，却很难等到 Feedback；也可能产生高质量 Review，却极少在下一次 Decision 中被检索。因此不能用“用户完成了模板”证明整套方法有效。

### 2.5 最低成本验证

第一轮验证不应依赖 Nine Rings 的新数据模型。可以先使用纸张或静态 Markdown 模板，将方法与以下基线比较：

- 实践者原有的普通笔记或自由复盘。
- 只记录 Decision、理由和 Outcome 的简单决策日志。
- 一次性的 Agent 引导会话。

建议按三个阶段推进：

1. **案例走查**：用若干已完成事项检查概念是否矛盾，但只用于发现结构问题，不能证明效果。
2. **前瞻性自用**：在 Outcome 出现前填写最小记录，验证闭环能否实际完成，并测量耗时和遗漏。
3. **小规模交叉试用**：让实践者在相似事项中交替使用自由记录和最小模板，比较可追溯性、解释质量、具体 Revision、后续复用及主观负担。

至少记录以下指标：

- 进入方法的事项中，事前记录和事后 Review 各自的完成比例。
- 事前记录、补充 Feedback 和完成 Review 的时间。
- 是否能够清楚区分 Prediction、Desired Outcome 与实际 Outcome。
- Review 是否提出了可检查的替代解释，而非只凭结果评价 Decision。
- Revision 是否具体说明改变前、改变后、依据和适用条件。
- 后续出现相似事项时，历史 Review 是否被检索，以及是否实际影响 Decision。
- 用户是否认为方法导致拖延、压力、过度记录或虚假的控制感。
- 对高风险事项，独立质询是否提出了此前未被记录的反证、替代解释或边界条件。

正式试验的通过阈值应在试点得到基线后事前冻结，不能看到结果后再选择有利指标。早期不宜用“目标成功率提高”作为唯一指标，因为样本小、事项异质，而且 Outcome 受到执行、环境和运气影响。

### 2.6 收缩或否定条件

如果长期出现以下结果，应缩小或放弃方法，而不是增加字段解释失败：

- 实践者在少量示例和说明后仍不能稳定区分核心概念。
- 大多数事项无法在合理时间内获得足以 Review 的 Feedback。
- Review 主要产生泛泛而谈的总结，没有具体 Revision 或使用条件。
- 历史 Review 很少在后续相似事项中被检索。
- 简单决策日志或一次 Agent 会话以更低成本产生相同效果。
- 记录负担导致更少行动、更多焦虑或明显的自我合理化。
- 观察到的改善主要来自投入了更多时间，而不是方法中的事前冻结、反馈分离和 Revision 机制。

### 2.7 当前最需要继续讨论的问题

1. **近端成功定义**：第一层优先证明“认知变化可追溯且可复用”，还是直接证明 Decision 质量改善？
2. **第一验证领域**：技术与产品 Decision 是否足够代表方法，还是只适合作为易获得 Feedback 的起点？
3. **最小记录边界**：Goal、Prediction、Success Criteria 中哪些必须显式记录，哪些可以合并表达？
4. **Revision 标准**：什么程度的变化才算 Revision，怎样避免把每次措辞调整都算成认知升级？
5. **复用证据**：仅仅检索历史 Review 是否足够，还是必须观察到后续 Decision 或 Action 改变？

当前建议是先把近端成功定义为：

> 实践者能够低成本地保留事前认知状态，依据现实 Feedback 形成可解释的 Revision，并在后续相似事项中实际调用它。

这比“帮助用户把所有事情做得更好”窄得多，但更接近可验证命题，也更能判断后续是否值得交给 Nine Rings 产品化。

### 2.8 为什么要同时保存行动前与行动后

如果只记录行动后的总结，实践者实际上在用“已经知道 Outcome 的自己”重建“当时还不知道 Outcome 的自己”。两者不是同一个信息状态。

结果出现后，人可能无意中：

- 高估自己原来对结果的预见程度。
- 忘记当时认真考虑过但最终没有发生的可能性。
- 把模糊判断回忆成明确 Prediction。
- 根据结果重新解释原 Goal 或 Success Criteria。
- 因为 Outcome 好而高估 Decision 质量，或者因为 Outcome 坏而否定当时合理的 Decision。

事前记录的作用不是证明当时判断正确，而是保存一个可以比较的认知基线。它至少应保留当时的语境、可得信息、关键 Unknown、当前判断、Decision、可观察预期和 Review Trigger。

```text
只有事后记录
  → 现在怎样解释过去

事前状态 + 事后记录
  → 当时怎样判断
  → 实际发生什么
  → 两者哪里不同
  → 现在为什么改变或不改变
```

但仅仅保存两个快照仍然不够。要产生学习，还需要三个转换：

1. **从差异到诊断**：差异来自认知、Decision、执行、环境、运气，还是测量方式？
2. **从诊断到 Revision**：原 Claim 应被加强、削弱、限定、替换，还是暂时维持？
3. **从 Revision 到复用**：下一次什么情境应检索它，准备怎样不同地判断或行动？

因此，“可靠保存”至少包含：

- 事前内容带有时间并且不能被无痕覆盖。
- 原始 Feedback 与后来解释分开。
- Success Criteria 的后续修改保留时间和理由。
- Revision 保留改变前、改变后、依据与适用条件。
- 后续相似事项能够找到并调用这次 Review。

这也说明方法的价值不是“记录更多”，而是提高跨时间比较的可信度，并把比较结果带回下一轮实践。

### 2.9 示例：Windows 桌面端启动假死

以下是用于说明方法的假设性案例，不代表对 Nine Rings 现有故障的实际诊断。

事项是：

> Windows 桌面端偶尔启动后停留在“加载中”，文档不可见，设置无法打开，关闭按钮也无效。

它值得进入闭环，因为影响较大、原因不确定、可以通过日志和测试获得 Feedback，而且启动流程的经验可能复用于后续开发。

#### 2.9.1 行动前

**事项与意图**

> 找出启动假死的原因，让应用即使初始化失败也能保持界面可操作，并显示明确错误。

这里的 Goal 不是“修改启动代码”，而是“应用能够可靠启动，或者进入可恢复的降级状态”。

**当前判断与可观察预期**

当前判断：

> 假死可能是 UI 在等待存储初始化完成，而初始化异常没有返回成功或失败状态。

关键 Unknowns：

- 是数据库读取过慢，还是 Promise 永远不结束？
- 关闭按钮是否也等待同一个初始化流程？
- 问题是否只发生在某些本地数据状态？
- 日志是否在初始化完成前就无法工作？

Prediction：

> 如果主要原因是初始化阻塞，那么人为让存储初始化不返回，应当稳定复现；增加超时和独立错误状态后，界面应当仍可关闭并进入错误页面。

Desired Outcome 是“希望应用不再假死”；Prediction 是“如果当前解释正确，注入初始化挂起就应复现问题”。两者不能混为一谈。

**Decision 与 Review Trigger**

Decision：

> 先编写初始化挂起和初始化失败的测试，不立即重构全部启动流程。

Action：

- 模拟存储初始化永远不返回。
- 模拟初始化抛出异常。
- 检查文档区、设置和关闭按钮是否仍可操作。
- 记录启动阶段日志。

Review Trigger：

> 测试能够稳定复现问题，或者收集到三次真实假死日志后进行 Review。

#### 2.9.2 结果出现后

假设收到的原始 Feedback 是：

- 初始化挂起时，文档区持续显示“加载中”。
- 设置页面也依赖同一个全局 loading 状态。
- 关闭按钮事件已经触发，但关闭前流程等待自动保存完成。
- 自动保存又等待尚未完成初始化的存储。
- 增加存储初始化超时后，文档区能够显示错误，但关闭按钮仍然无效。

这些是观察结果。“根因是自动保存死锁”仍然是待检查的解释，不能直接写成 Reality。

Review 可以得出：

- “存储初始化阻塞整个 UI”的判断得到部分支持。
- 增加初始化超时没有解决关闭问题，说明原来的单一根因假设不完整。
- 关闭失败还有一条独立链路：关闭流程等待自动保存，而自动保存依赖存储初始化。
- 认知问题是过早假设只有一个根因。
- 设计问题是多个界面能力共享一个可能永久等待的全局状态。
- 测量问题是只有“是否加载完成”，缺少初始化各阶段的状态记录。
- 真实用户环境中的触发条件仍未确认。

Revision 可以写为：

```text
原认识：
启动假死主要是存储初始化没有超时。

修订后：
启动可靠性不能只通过给初始化增加超时解决。
应用外壳、数据加载、设置和关闭流程需要独立的失败、取消与降级路径，
不能共同依赖一个可能永久等待的全局状态。

未确认：
尚未证明真实用户的假死由哪一种数据或环境条件触发。

复用条件：
以后设计任何启动阶段服务时，检查超时、错误、取消、降级，
以及关闭操作是否依赖该服务成功完成。
```

这次 Revision 没有因为一个测试结果就宣布“已经找到全部根因”，但它形成了下一次可复用的工程判断。

### 2.10 为什么《乌合之众》不适合作为第一验证案例

阅读《乌合之众》当然可能改变认知，例如形成候选 Claim：

> 人在群体中更容易受到情绪传播和身份认同影响。

但它不是验证最小方法的理想起点：

- Claim 范围太大，“群体”和“影响”都没有明确边界。
- 很难在短期内获得足以归因的 Feedback。
- 实践者很容易只注意支持该观点的案例。
- 现实行为受文化、角色、权力、议题和观察方式等大量变量影响。
- 书中的历史背景、论证方法与现代研究未必一致。

可以把它缩小成可观察 Prediction：

> 在观点高度一致且身份公开的小组讨论中，我会比独立书面判断时更少表达反对意见。

然后比较会前独立判断、实际发言、会议结构和会后解释。但这里仍存在自我报告偏差、观察者效应和样本不足。

因此，技术排障、产品取舍和学习策略更适合作为第一验证领域。它们不一定更重要，只是 Feedback 更快、变量更容易观察、Revision 更容易在相似事项中复用。只有在这些较容易验证的领域成立后，才值得谨慎扩展到阅读形成的宽泛社会 Claim。
