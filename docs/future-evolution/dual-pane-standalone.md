# 双栏浏览独立产品评估

日期：2026-11-10。状态：共享核心及界面已接入两种宿主；独立 Web 原型已支持共享源码编辑、安全保存与恢复草稿，原生独立应用与安装包待实现。

## 判断与定位

可以演进为独立产品。建议定位为面向开发者的本地双栏文件工作台：浏览、可核对的文件操作、目录比较、快速预览和源码/Markdown 查看。先做好这组闭环，再决定是否扩展归档、远程文件服务或完整 IDE；不把 Nine Rings 的数据库文档、同步、词汇学习等能力全部带入。

现有入口已是可单独启停的可信内置插件，但它仍运行在 Nine Rings 宿主中。“插件独立”不等于“应用已经独立”。[现有双栏契约](../plugins/plugin-dual-pane-browser.md)及[宿主边界决策](../decisions/002-dual-pane-file-browser.md)继续有效。

## 已有基础与实际耦合

可复用的基础包括每栏导航/标签状态、分页和排序、比较预算、拖放确认、操作队列、结果历史，以及原生的授权目录读取、摘要与安全传输。写入继续要求明确确认、草稿预检、排他发布及未知结果人工核对；独立产品不能简化这些约束。

尚不能直接复制组件发布：

| 位置 | 当前依赖 | 拆分时应保留的职责 |
| --- | --- | --- |
| `src/lib/local-files/browser-provider.ts` | 插件身份、主区域视图、最近文件、焦点标签、编辑检查点 | 在授权范围内读取和打开文件，正确交接当前编辑器 |
| `src/lib/local-files/browser-operations.ts` | 会话、草稿、路径状态迁移、主区域身份 | 移动成功后迁移打开文件；未知结果不伪装成功 |
| `src/lib/local-files/service.ts` | 工作区面板、插件权限、授权、会话与操作锁 | 保留宿主权限与写入所有权 |
| `src/components/LocalFileView.tsx` | 共享编辑/渲染、菜单、状态栏与导航 | 复用一份编辑模型，不再复制第二套文件编辑器 |

## 第一批实施：共享核心

已将文件模型、目录读取/摘要/预览、操作执行器和串行队列抽成同目录下的可移植模块：`file-model.ts`、`browser-contract.ts`、`browser-provider-core.ts`、`browser-operation-contract.ts`、`browser-operation-core.ts`、`browser-queue-core.ts`。路径检查、比较、排序、导航等原有纯逻辑继续复用，没有复制另一套实现。

Nine Rings 原有 `browser-provider.ts`、`browser-operations.ts`、`browser-operation-queue.ts` 保留公开调用方式，并实际委托这些核心。宿主必须提供授权、文件服务、打开文件、草稿检查、操作租约及移动/删除后的状态协调；队列结果历史通过可选持久化端口接入。共享核心不读取插件单例、主区域或浏览器存储。现有文件服务仍执行实际授权与路径安全检查。

两个隔离宿主的契约测试覆盖读取撤权、打开文件失败、移动协调、队列串行与取消；导入边界测试防止核心重新引入应用模块。它们证明核心可以脱离 Nine Rings 服务装配。第二批进一步处理界面依赖，形成下述只读原型；原生写入和编辑生命周期仍不能用空保存检查代替。

实现决策和保护规则见[共享核心决策](../decisions/003-shared-file-workbench.md)。

## 第二批实施：独立 Web 入口

共享的 `FileBrowserWorkspace` 由两个入口装配：

- Nine Rings：`DualPaneFileBrowser` 保留原插件接口，经 `createNineRingsBrowserHost` 接入目录授权、原有队列、设备设置、保存门禁及主区域打开。
- File Workbench：`file-workbench.html`、`src/apps/file-workbench/main.tsx` 与 `host.ts`，按能力装配服务（第二批只读，第三批支持文本保存）；不启动 Nine Rings App、文档数据库、内置插件集、同步或 Service Worker。暂用 File Workbench 作为工作名称。

两者复用相同的列表、目录标签、路径、分页、排序、多选、快速预览、目录比较和正文搜索组件。根目录读取/选择、能力、绝对路径、状态存储、队列和变更通知由 `BrowserWorkspaceHost` 指定。共享界面缺少宿主时明确报错，不偷偷使用 Nine Rings 单例。可编辑查看器的进一步装配不在本批伪造。

### 运行与构建

```bash
npm run dev:workbench
# http://127.0.0.1:1421/file-workbench.html

npm run build:workbench
npm run preview:workbench
# http://127.0.0.1:1421/file-workbench.html
```

构建只输出到 `.local-tools/file-workbench-dist/`，依赖优化缓存单独保存；不会覆盖 `dist/`，也不向 Nine Rings 的更新入口发布。构建门禁拒绝引入 `App.tsx`、Nine Rings `main.tsx`、文档 API 或数据库适配器入口。独立原型的设置键使用 `file-workbench:` 前缀，包含浏览状态、列宽、常用目录与配色；队列历史暂不启用，不读取或清理 Nine Rings 历史。正式部署须使用独立 origin，不在 Nine Rings 的 PWA scope 下部署；默认开发端口有助于隔离浏览器授权。

### 第三批：共享源码查看、编辑与保存

文本打开改用与 Nine Rings 本地文件相同的 `DocumentSourceSurface` / `MarkdownSourceEditor`：语法着色、查找、折叠、选区/右键菜单、格式化、撤销等来自原实现。文本读取遵循原文件服务的 UTF-8/二进制检查和 4 MiB 上限，不再使用快速预览的 1 MiB / 65536 字符截断。搜索结果根据原始快照修订定位，不能将过期偏移应用到已变化文件。图片仍复用原来的只读预览。

打开文本默认只读，点击“允许编辑”后可修改。目录快照只能导出副本；支持写入的授权目录在显式保存时请求浏览器权限，并通过同一文件服务验证原始修订，外部变化时拒绝覆盖并提供差异比较。未提供强制覆盖快捷入口；可导出当前副本，或在保留草稿后重新读取磁盘。

`saveLocalSource` 被 Nine Rings 本地编辑器和独立宿主共同调用：先接收磁盘回执并更新基线，再处理恢复草稿；保存期间的新编辑以新基线保留。草稿更新或宿主收尾失败不能把已经完成的磁盘写入变成可盲目重试的失败，也不能宣告当前编辑全部保存。副本下载复用 `source-download.ts`，保留 BOM 和换行约定，导出后仍标记原文件未保存。

恢复草稿使用同一 `createLocalDraftStore` 实现，数据库独立为 `file-workbench-local-recovery`，旧 Nine Rings 数据库名称、结构和默认 API 保持不变。独立宿主选择 `retainUntilResolved` 策略，不自动过期或淘汰未处理草稿；达到五份上限时拒绝新事务并保留现有记录，须在草稿入口下载并确认删除旧记录，或保存当前文件。每个数据库的同一身份共享有序事务，写入与删除确认以事务完成为准；过期清理须核对旧值，不能删除刚发布的新草稿。离开时可保存、保留已确认持久化的草稿，或取消；失败继续保留编辑器、文本和撤销历史。

### 当前范围与限制

支持真实授权目录（浏览器支持时）或目录快照，保留同源双栏浏览、比较、搜索和图片预览。原型还不是独立桌面安装版，不开放目录变更队列；文件内容写入和目录操作是两个装配边界。源码工具的偏好沿用共享字段结构，依赖独立 origin 隔离；浏览状态/列宽/常用目录/配色继续带独立前缀。

目录句柄和快照仅在当前会话有效，重新启动需重新授权；重新授权的身份不同，不自动将旧草稿套用到可能只是同名的文件。“恢复草稿”入口可查看和下载此前内容，核对路径后手动恢复。同一会话重开文件可显式恢复对应草稿。强制关闭页面或进程只能尽力暂存；未保存编辑触发浏览器退出提示，不承诺异步事务在强制终止后必然完成。

完整 Markdown/Flow/Mermaid 渲染工作区、目录/符号/书签的宿主装配、位置与打开文件状态恢复、原生安全操作及安装包继续分批处理。原型不会为追求一次性复用而引入数据库文档 API，也不会复制第二套编辑器。

独立 Playwright 配置 `playwright.workbench.config.ts` 使用自己的 1421 端口，真实目录快照验证浏览、预览、比较、工作线程搜索及设置隔离。它从 Nine Rings 默认 E2E 计划排除，由 Test workflow 中的独立 Chromium/WebKit 步骤针对生产产物执行，避免在错误宿主上重复运行。构建后可使用 `NR_WORKBENCH_PREVIEW=true npx playwright test --config playwright.workbench.config.ts --browser=chromium` 验证生产资源路径，默认配置测试开发入口。

## 推荐边界

同仓库维护可复用核心和两个应用装配入口。Nine Rings 使用现有宿主适配器；独立应用使用自己的适配器。先通过少量明确接口切断宿主耦合，再考虑物理移动目录，不先复制整个应用再删功能。

宿主接口至少覆盖：授权文件服务、文件打开/关闭、未保存内容检查、编辑检查点与路径迁移、设置/主题、剪贴板、通知。它们表达实际能力和失败语义，不能以空实现绕过草稿或权限检查。原生文件操作也应抽取共享 Rust 库，而非维护两份安全传输实现。

独立应用必须有独立的 bundle identifier、用户数据目录、授权记录、设置、更新通道和发布产物。Nine Rings 的打开文件/最近访问数据不能因安装另一个应用而被覆盖。

## 分阶段实施

1. **边界准备**：在现有插件内部引入宿主适配接口，保持用户行为不变。用原有浏览、保存失败、停用清理、移动迁移回归验证接口真实可用。
2. **最小独立宿主**：复用双栏和现有本地文件查看器，仅装配必要的服务。打通目录授权、浏览、操作、预览、编辑及退出前保存。此时再评估共享模块应成为哪些包。
3. **独立交付**：完成安装包、设置、快捷键、主题、状态恢复、更新与跨平台门禁；补齐真实权限、跨卷、系统回收站及异常退出验收。
4. **产品扩展**：依据实际需求选择远程提供者、归档、Git 等能力，分别定义权限和错误恢复，不提前承诺所有系统文件管理器功能。

优先桌面 Tauri 三平台。Web 可继续提供已授权目录的受限版本，但不承诺完整磁盘路径、后台任务及系统回收站等原生能力。自动化浏览器夹具不替代三平台真实文件系统验收。

## 投入与验证

主要成本是宿主边界、应用生命周期和交付，不是重新画两栏。独立可运行原型与可日常使用的产品应分开估算；未验证依赖拆分前不提供精确工期。先以一轮边界准备统计需改动的接口、编辑器依赖和打包结果，再估算后续工作。

推荐的检查层次：核心状态/队列单元测试；共享交互 E2E；两个宿主分别运行保存门禁和资源生命周期契约；三平台原生文件操作与打包；真实跨卷、授权撤回、外部变化和崩溃后的人工核对。复制/移动成功率之外，重点记录错误是否明确、是否误重试及打开文件身份是否保持。

成熟产品可参考 [Double Commander 的双栏定位](https://doublecmd.github.io/doc/en/about.html)和[目录同步工作流](https://doublecmd.github.io/doc/en/syncdirs.html)。应用拆分应保留 [Tauri 权限边界](https://v2.tauri.app/security/permissions/)，而不是为了独立发布而扩大所有窗口的文件访问权限。
