# 插件适配版本与发布计划

## 1. 基线

`v0.1.0` 为注释标签，指向 `05e624afe40c4bc6c55b5576e412074815147ac4`，标记插件适配前的已提交代码。本设计文档是标签之后的工作，不在基线提交中。创建本地标签不等于已推送标签或创建 GitHub Release。

## 2. 首次代码实现的版本提升

本次只修改设计文档和 README，产品版本保持 `0.1.0`。计划在首次实现插件宿主的代码提交中提升至 `0.2.0`，同步以下产品版本来源：

| 文件 | 需要同步的内容 |
| --- | --- |
| `package.json` | 应用 `version` |
| `package-lock.json` | 根版本与根 package 版本 |
| `src-tauri/Cargo.toml` | 本应用 package 版本 |
| `src-tauri/Cargo.lock` | `nine-rings` 自身条目的版本，保留其它依赖版本 |
| `src-tauri/tauri.conf.json` | 桌面应用打包版本 |
| `src/lib/app-changelog.ts` | 当批实际实现的用户可见变更 |

Flutter 的具体插件适配留待后续，不顺带变更其版本或安装工具。源码中的构建标识目前由 `vite.config.ts` 使用提交 hash 和时间生成，有 git 时不是产品语义版本；实现阶段需要决定如何同时展示 `0.2.0` 产品版本与构建标识。不要因版本展示调整改变 Service Worker 识别新部署的构建唯一性。

## 3. 版本职责

| 版本 | 管理的对象 | 原则 |
| --- | --- | --- |
| 产品版本 | 整个应用发布 | 首次代码实现从 `0.1.0` 提升至计划的 `0.2.0` |
| SDK/API 版本 | 公共调用语义 | 首期 `0.x` 试验；改变契约时显式提高兼容范围 |
| 插件版本 | 某个插件包 | 独立更新，声明兼容 API 与平台 |
| 内容格式版本 | 可持久化块/插件数据 | 无损迁移、旧内容回退；不能只靠插件版本判断 |

在试点通过之前不宣布 SDK 已稳定。未来 tag/发布应指向通过相应验证的提交；不要移动当前基线标签到后续实现提交。
版本职责和稳定性边界以[插件体系设计](plugin-system-design.md)为准。
