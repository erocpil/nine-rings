# 大文件正文局部渲染评估

> 日期：2026-09-05；初始评估基线：`f9da95e`。下方保留初始分析，文末记录随后实现的**默认关闭的只读窗口化原型**及生产构建 A/B 数据。iPhone PWA 与 Windows Tauri 真机验证仍由用户执行。

## 结论

值得验证局部渲染，但应先针对**只读阅读模式**制作可关闭的原型，暂不替换可编辑正文。当前测量更支持优先降低首次内容构建/布局成本，而非继续扩大左侧标记预读范围。没有局部渲染原型的对照数据，不能承诺具体提速比例。

## 当前架构

- `NoteEditor.tsx` 使用一个 TipTap `EditorContent`；ProseMirror 保存完整文档模型，正文顶层节点全部挂载。
- `EditorBlockGutter.tsx` 仅对可视区及预读块挂载标记，按折叠后的布局顺序定位，空白处二分查找边界。它不是正文虚拟化。
- `DocumentOutlineList.tsx` 已有目录窗口化；目录节点不参与原生正文选区，因此其方案不能直接套到正文。
- 标题折叠隐藏已有节点，不删除文档模型。搜索定位、书签、块号、原生选区、只读双击及编辑器位置恢复仍依赖模型位置与 DOM 的对应关系。

## 可重复基线

```sh
NR_EDITOR_BENCHMARK=1 npx playwright test e2e/editor-rendering-benchmark.spec.ts --workers=1
NR_EDITOR_BENCHMARK=1 npx playwright test e2e/editor-rendering-benchmark.spec.ts --workers=1 --browser=webkit
```

默认 E2E 跳过该诊断用例，不将机器相关的耗时设为 CI 成败阈值。两个浏览器顺序运行，避免共享测试服务器退出及并行负载干扰。

环境：本机 Linux、无头 Chromium/WebKit、Vite 开发构建，未模拟移动设备 CPU。每 30 块一个标题，普通段落包含重复的中英文、加粗标记；先在桌面视口粘贴，等待保存，再切换 390×852 只读专注模式，跨文档均匀滚动 41 帧。每个规模/引擎本轮各测一次，是诊断样本，不是统计性能承诺。

| 引擎 | 块数 | 粘贴事件同步耗时 ms | 粘贴至两帧及布局读取完成 ms | 正文元素数 | 滚动帧间隔 P95 ms | 滚动几何读取次数 |
|---|---:|---:|---:|---:|---:|---:|
| Chromium | 300 | 73 | 376 | 1,170 | 17.3 | 162 |
| Chromium | 1,500 | 188 | 1,566 | 5,850 | 17.1 | 189 |
| Chromium | 5,000 | 670 | 4,702 | 19,499 | 18.7 | 206 |
| WebKit | 300 | 397 | 468 | 1,170 | 17.0 | 162 |
| WebKit | 1,500 | 1,032 | 1,086 | 5,850 | 17.0 | 189 |
| WebKit | 5,000 | 3,564 | 3,659 | 19,499 | 17.0 | 210 |

解释与边界：

- 顶层 DOM 块数始终等于 300/1500/5000，证实正文仍全量挂载。
- 41 帧内几何读取仅由约 160 增至约 210，未随正文节点数同比增长；已有 gutter 窗口化确实在限制滚动测量成本。
- 首次构建/布局等待随规模明显增长，但该指标包含 Markdown 解析、编辑事务、扩展更新与布局，**不能全部归因于浏览器布局**，也不是“打开已有文件耗时”。后续需要分阶段 profile。
- 本次未测 JS 堆/进程内存、生产构建冷启动、图片/表格密集正文、真实触摸惯性滚动或后台恢复。DOM 数量只能说明规模，不能当作内存节省实测值。

## 借鉴成熟方案

CodeMirror 显式维护 viewport、排除折叠内容的 visible ranges 及视口外高度信息，并分阶段执行布局测量。可借鉴其“共享可见范围、高度索引、读写分离”设计，不意味着应更换编辑器。[官方系统说明](https://codemirror.net/docs/guide/)

ProseMirror 管理文档选区与 DOM 选区的对应关系，NodeView 的内容可以由编辑器管理或由应用接管。由此推断：直接移除不可见的可编辑节点不是简单列表优化，需要同时承担选区与内容管理责任。[官方指南](https://prosemirror.net/docs/guide/)

## 方案比较

| 方案 | 预期收益 | 主要风险 | 建议 |
|---|---|---|---|
| 单纯增加 gutter 预读数量 | 不减少正文 DOM 或首次构建成本 | 掩盖可见范围算法错误，增加观察/测量负担 | 不作为正文优化 |
| 对整个可编辑正文强行跳过屏外布局 | 可能减少部分布局成本，不减少完整文档模型 | 估算高度漂移、DOM 坐标、选区、中文输入法及跨屏复制 | 不直接上线 |
| 独立只读窗口化渲染 | 有机会限制挂载节点和首次渲染成本 | 长选区复制、搜索命中、书签、折叠及图片后加载引发高度变化 | 优先做受控原型 |
| 改写可编辑正文的渲染窗口 | 理论覆盖阅读与编辑两种模式 | 必须处理 IME、撤销、拖选、跨块粘贴、插件及无障碍语义 | 成本高，暂缓 |

## 原型边界与验收条件（后续建议，尚未实现）

1. 保留完整文档模型及稳定块位置，只对只读显示层窗口化；目录、正文和 gutter 共用折叠后的块索引与高度缓存。
2. 按像素范围预读，未知高度先估算，再用有限测量修正；用“可见块位置＋块内偏移”保持滚动锚点，不能仅保存绝对 scrollTop。
3. 搜索/书签跳转先挂载目标块，再计算坐标；复制全文和导出从模型生成，不能只复制已挂载 DOM。
4. 跨窗口选区、打印、图片和表格需有明确策略；需要完整原生选区时可退回完整渲染。切换可编辑模式必须还原全文并恢复位置。
5. 使用相同 300/1500/5000 块与真实大文档进行生产构建 A/B 测量；至少重复三次并记录中位数。只有首次显示/挂载规模有明确改善，且搜索、书签、末尾折叠、选区复制、后台恢复全部通过，才考虑默认启用。

以上为实施前的评估，不代表已经验证的收益。

## 后续：只读窗口化实验原型

入口：**设置 → 高级 → 只读正文局部渲染（实验）**。默认关闭，仅保存在当前设备的 `nr:experimentalReadonlyRendering`，不进入同步/备份配置。开启后对支持的只读文档生效；“完整渲染”按钮可在当前打开会话中回退，关闭实验开关则全局回退。可编辑文档仍使用原编辑器。

### 实现边界

- `NoteEditor` 在创建编辑器之前选择显示路径。局部阅读只构建完整 ProseMirror 文档模型，**不创建隐藏的 EditorView，也不为每个块创建子编辑器**。
- 支持段落、标题、硬换行、列表、引用、代码块和基础行内格式。图片、表格、未知节点/标记、非 HTTP(S)/邮件/电话的特殊链接、超过 50,000 模型位置单位的顶层单块，以及 Vim/摘录来源特殊界面自动使用完整编辑器。
- 正文和 gutter 渲染同一份折叠后块序列，保留原始块号。高度索引在测量或折叠时更新，滚动窗口使用二分查找及像素预读；不依赖屏外正文的 IntersectionObserver 回调。
- 保存“块位置＋块内偏移”，可刷新恢复，并在只读/编辑及完整/局部渲染切换时交接位置。代码、引用的临时阅读状态独立于窗口内块组件，离屏再回来不会重置；这些覆盖状态暂不写入正文或跨设备同步。
- 搜索遍历完整模型，先展开所属标题及引用/代码块，再挂载目标，最后测量命中文字的位置。已有书签可跳转，管理书签切回完整渲染。
- 原生选区存在时保留涉及的连续窗口，不回收选区 DOM；因此长选区期间可能增加挂载数量。全文复制直接从模型生成，不读取局部 DOM。
- 按钮打开浮层，触屏专注模式右侧边缘手势打开现有阅读侧栏。标题触摸双击受原只读折叠选项控制。

### 暂不承诺的功能一致性

原型不是完整阅读器替代品：代码语法高亮/代码行号、目录高级停靠和长按行为、全文原生选择、原生查找、打印及无障碍全文遍历仍需完整渲染。自带全文复制/搜索不受挂载范围限制。局部模式打印会明确提示切换，避免输出看似完整的残缺正文。当前状态栏仅显示块数及挂载数量。

仍保留完整模型和索引，因此它是**局部渲染，不是数据库分块加载**；文档解析和模型内存仍随全文规模增长。暂不默认启用，也不据此次测试确定自动启用块数门槛。

### 生产构建 A/B

```sh
npm run build
NR_READONLY_BENCHMARK=1 npx playwright test --config playwright.readonly-benchmark.config.ts
NR_READONLY_BENCHMARK=1 npx playwright test --config playwright.readonly-benchmark.config.ts --browser=webkit
```

两种引擎顺序运行，无并行构建/测试负载。Linux 无头浏览器，390×852 视口；直接在隔离 IndexedDB 中准备已有只读文档，每 30 块一个标题，其余为中英文段落；不走粘贴流程。每次新建页面、保留同一浏览器上下文，交替完整/局部模式顺序，各取三次。关闭 Service Worker。不是设备冷启动或 iPhone/Windows 真机测试。

指标为页面导航起点至目标首屏正文挂载、两帧及布局读取完成；包括应用启动，不是纯布局时间，也不表示所有异步任务已经结束。

| 引擎 | 块数 | 完整模式三次 ms | 局部模式三次 ms | 中位数：完整 → 局部 ms | 首屏挂载块：完整 → 局部 |
|---|---:|---|---|---|---|
| Chromium | 1500 | 611 / 604 / 529 | 198 / 255 / 233 | 604 → 233 | 1500 → 14 |
| Chromium | 5000 | 1654 / 1368 / 1260 | 294 / 328 / 344 | 1368 → 328 | 5000 → 14 |
| WebKit | 1500 | 1940 / 1747 / 1641 | 600 / 532 / 456 | 1747 → 532 | 1500 → 14 |
| WebKit | 5000 | 7737 / 7478 / 7480 | 491 / 522 / 518 | 7480 → 518 | 5000 → 14 |

完整模式正文元素为 1500/5000，局部模式正文含块包装与 gutter 共 59 个元素。该数字不能直接当作内存节省比例。样本仅为普通段落/标题；复杂文档、长列表、代码密集内容、滚动帧率和真机内存仍需补测。原型功能也是完整模式的子集，因此不能把上述比例当作最终功能齐全版本的提速承诺。

功能回归位于 `e2e/readonly-rendering.spec.ts`，涵盖 1500 块窗口、末章反复折叠、搜索/书签、代码引用状态、刷新位置、原生选区及触屏入口；模型边界测试位于 `tests/unit/readonly-rendering.test.ts`。性能用例默认跳过，不以毫秒数作为 CI 门槛。
